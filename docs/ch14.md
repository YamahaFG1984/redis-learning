# 第 14 章（补充）可观测性与生产排障

> 本章是原书没有覆盖的内容。原书第 4 章讲了"怎么用 `redis-benchmark` 对比吞吐率"，但完全没有涉及**上线之后怎么持续监控、怎么在出问题时快速定位**——这在今天是任何生产 Redis 部署都绕不开的一课。本章补上这块内容。

## 14.1 内置诊断命令

### 慢查询日志 SLOWLOG

```bash
CONFIG SET slowlog-log-slower-than 10000   # 单位微秒，超过 10ms 记录
CONFIG SET slowlog-max-len 1000
SLOWLOG GET 10     # 查看最近 10 条慢查询
SLOWLOG RESET
```

`SLOWLOG` 记录的是**执行阶段**的耗时，不包括排队等待时间——如果整体延迟很高但 `SLOWLOG` 里都是正常的，问题很可能出在网络排队/客户端侧，而不是 Redis 命令本身太慢。这是排查"应用感知延迟高，但 SLOWLOG 看着正常"这类问题时最容易被忽视的一点。

### 延迟监控 LATENCY

```bash
CONFIG SET latency-monitor-threshold 100   # 单位毫秒
LATENCY HISTORY event         # 查看某类延迟事件的历史（如 command、fork、fast-command）
LATENCY LATEST                # 所有类别的最新一次延迟事件
LATENCY DOCTOR                # Redis 自己给出的诊断建议（文字形式，很实用）
```

`LATENCY DOCTOR` 是一个经常被忽略但很好用的命令——它会根据当前记录的延迟事件，用自然语言直接告诉你"你的 fork 耗时偏高，可能是数据集太大/AOF 重写太频繁"这类结论，等于内置了一份自动化的排障报告。

### 内存分析

```bash
MEMORY USAGE mykey             # 单个 key 占用的字节数
MEMORY STATS                   # 整体内存分布（dataset、overhead、fragmentation 等）
MEMORY DOCTOR                  # 类似 LATENCY DOCTOR，给内存问题的自动诊断
redis-cli --bigkeys            # 扫描找出各类型里最大的 key（生产环境建议在从库上跑）
redis-cli --memkeys            # 按估算内存占用排序找大 key（较新版本 redis-cli 支持）
```

**`--bigkeys`/`--memkeys` 的重要提醒**：这两个工具本质是全量扫描（基于 `SCAN`，比原书年代直接 `KEYS *` 安全，但依然会给 Redis 带来额外负载），**生产环境建议在只读从库上跑，而不是主库**，且尽量避开业务高峰期。

### 客户端连接诊断

```bash
CLIENT LIST                    # 查看所有连接，包括每个连接的空闲时间、正在执行的命令
CLIENT INFO                    # 当前连接自身的信息
INFO clients                   # 连接数统计
```

原书第 4 章的"25%~30% 基准吞吐 = 每次都在新建连接"这条经验法则依然成立，`CLIENT LIST` 是验证这个猜测最直接的手段——如果看到大量连接的 `age` 都是 0 或很小，说明客户端确实没有复用连接。

## 14.2 内存淘汰策略：maxmemory-policy

原书完全没有讨论"内存满了怎么办"，但这是生产环境几乎必然会遇到的问题。Redis 提供 8 种淘汰策略：

| 策略 | 行为 |
|---|---|
| `noeviction`（默认） | 内存满后拒绝写入，返回错误 |
| `allkeys-lru` | 所有 key 里淘汰最近最少使用的 |
| `allkeys-lfu`（4.0+） | 所有 key 里淘汰访问频率最低的 |
| `allkeys-random` | 所有 key 里随机淘汰 |
| `volatile-lru` | 只在设置了 TTL 的 key 里淘汰 LRU |
| `volatile-lfu` | 只在设置了 TTL 的 key 里淘汰 LFU |
| `volatile-random` | 只在设置了 TTL 的 key 里随机淘汰 |
| `volatile-ttl` | 优先淘汰剩余 TTL 最短的 key |

**如何选择**：如果 Redis 是纯缓存（数据丢了可以从数据库重新加载），用 `allkeys-lru` 或 `allkeys-lfu`（LFU 更适合"有些 key 被频繁访问、有些几乎不被访问"这种长尾分布场景，比如热点商品缓存）。如果 Redis 里既有缓存数据又有不能丢的业务数据（如队列、计数器），**必须用 `volatile-*` 策略，并且给可以被淘汰的 key 显式设置 TTL，给不能丢的 key 不设置 TTL**——`noeviction` 策略下，一旦内存打满，所有写命令（包括看似无关的业务写入）都会开始报错，这是很多生产事故的根源，排查时第一时间应该检查 `INFO memory` 里的 `used_memory` 是否逼近 `maxmemory`。

## 14.3 指标采集：Prometheus + Grafana

原书第 5 章推荐 Graphite 做统计可视化，今天最主流的组合是 **Redis Exporter + Prometheus + Grafana**：

```bash
docker run -d --name redis-exporter -p 9121:9121 \
  oliver006/redis_exporter --redis.addr=redis://redis:6379
```

Prometheus 配置抓取目标后，Grafana 直接导入官方的 Redis Dashboard（Grafana.com 上有现成的公开面板模板），核心要盯的指标：

- `redis_connected_clients` —— 连接数是否异常增长（连接泄漏的信号）。
- `redis_memory_used_bytes` vs `redis_memory_max_bytes` —— 内存逼近上限的预警线。
- `redis_commands_processed_total`（配合 rate() 看 QPS 趋势）。
- `redis_keyspace_hits_total` / `redis_keyspace_misses_total` —— 缓存命中率，命中率骤降往往意味着缓存被绕过或者刚发生过大规模淘汰。
- `redis_rdb_bgsave_in_progress` / `redis_aof_rewrite_in_progress` —— 持久化操作是否在进行，配合应用层延迟毛刺做关联分析（回想第 4 章讲的 fork 停顿问题）。
- `redis_replication_lag` —— 主从复制延迟，读从库的场景要特别关注这个指标，延迟过高意味着从库读到的是旧数据。

## 14.4 Redis 自带的可视化工具：RedisInsight

Redis 官方提供免费的图形化管理工具 **RedisInsight**，可以直接连接实例查看：key 空间分析（按前缀统计内存占用分布，比手写脚本扫描方便很多）、慢查询日志可视化、内存分析、Profiler（实时看命令流）、以及 CLI。对于原书第 9 章讲的"哪些 key 该分片/该压缩"，RedisInsight 的内存分析视图能直接可视化出"哪类 key 前缀占用了最多内存"，比手写扫描脚本效率高得多。

## 14.5 三语言下的健康检查与基础指标暴露

**Python（Django 健康检查端点）**

```python
# views.py
from django.http import JsonResponse
from django_redis import get_redis_connection

def health_check(request):
    try:
        conn = get_redis_connection("default")
        info = conn.info()
        return JsonResponse({
            "status": "ok",
            "connected_clients": info["connected_clients"],
            "used_memory_human": info["used_memory_human"],
            "hit_rate": info["keyspace_hits"] / max(1, info["keyspace_hits"] + info["keyspace_misses"]),
        })
    except Exception as e:
        return JsonResponse({"status": "error", "detail": str(e)}, status=503)
```

**Java（Jedis，暴露关键 INFO 字段）**

```java
public Map<String, String> healthCheck(UnifiedJedis jedis) {
    String info = jedis.info();
    Map<String, String> stats = new HashMap<>();
    for (String line : info.split("\r\n")) {
        if (line.startsWith("connected_clients:") || line.startsWith("used_memory_human:")) {
            String[] kv = line.split(":", 2);
            stats.put(kv[0], kv[1]);
        }
    }
    return stats;
}
```

**TypeScript（Hono.js 健康检查端点）**

```ts
import { Hono } from "hono";
import { Redis } from "ioredis";

const redis = new Redis();
const app = new Hono();

app.get("/health/redis", async (c) => {
  try {
    const info = await redis.info();
    const parsed = Object.fromEntries(
      info.split("\r\n").filter((l) => l.includes(":")).map((l) => l.split(":") as [string, string])
    );
    return c.json({
      status: "ok",
      connectedClients: parsed["connected_clients"],
      usedMemory: parsed["used_memory_human"],
    });
  } catch (e) {
    return c.json({ status: "error", detail: String(e) }, 503);
  }
});

export default app;
```

## 14.6 生产排障速查表

| 现象 | 优先检查 |
|---|---|
| 应用延迟高，SLOWLOG 正常 | 网络排队/客户端连接池配置；`CLIENT LIST` 查连接数 |
| 内存持续增长 | `MEMORY STATS`/`--bigkeys`；确认 `maxmemory-policy` 和 TTL 设置是否合理 |
| 写入突然报错 OOM | `INFO memory` 检查是否逼近 `maxmemory`；策略是否为 `noeviction` |
| 周期性延迟毛刺 | 关联 `redis_rdb_bgsave_in_progress`/AOF 重写时间点（第 4 章 fork 开销） |
| 命中率骤降 | 检查是否刚发生大规模淘汰，或缓存 key 设计变更导致穿透 |
| 从库读到旧数据 | `INFO replication` 查 `master_repl_offset` 与从库偏移量的差距 |
| 连接数异常增长 | 排查是否有客户端连接泄漏（未正确关闭/复用连接） |

## 本章小结

原书对"上线后怎么办"几乎是空白——这符合当时的技术生态（Prometheus 2015 年才发布，Grafana 更晚才成熟）。今天一套完整的 Redis 生产实践必须包含可观测性这一环：内置的 `SLOWLOG`/`LATENCY`/`MEMORY` 系列命令负责"现场排障"，Redis Exporter + Prometheus + Grafana 负责"长期趋势监控和告警"，RedisInsight 负责"图形化探索"。这三层工具配合，才能把原书第 4 章那种"靠经验法则手工排查"的方式，升级成有数据支撑的系统化运维。
