第 10 章

第 10 章 扩展 Redis

对应原书第 10 章 "Scaling Redis"。重要背景：本书写于 2013 年，Redis Cluster 直到 Redis 3.0（2015 年）才正式发布，所以这一整章教的是"官方分片方案出现之前，工程师如何手工搭建分片系统"。今天这一章最大的价值是理解 Redis Cluster 到底自动化了哪些原本要手写的工作——本文会逐节对照。

10.1 扩展读

分片之前先做的检查清单（原书列的，至今适用）：紧凑结构的阈值没设太大（第 9 章）、用对了数据结构（比如该用 ZSET 就别整个 HASH 拉回来客户端排序）、大对象考虑压缩、用了连接池和 pipeline。

只读从库

配置 slaveof/SLAVEOF（现代命令名是 REPLICAOF，见第 4 章），把读流量分散到从库。原书提醒重连从库会丢弃它原有的全部数据，以及默认从库拒绝写入。

从库重连的带宽问题与两种缓解方案

多个从库同时重连会共享同一份快照传输（高效），但同时给多个从库推送快照可能打满带宽，导致延迟飙升甚至连累其他已连接的从库掉线。原书给的两个方案：

  1. 复制树：主库→若干中间从库→更多叶子从库，用于跨机房/跨广域网复制（原书图示：1 主 → 3 中间从库 → 9 叶子从库）。代价是拓扑复杂化，故障切换更麻烦。
  2. 压缩隧道：用带压缩的 SSH 隧道传输复制流量（原书举了一个真实例子：21Mbps 降到 1.8Mbps）。

现代变化：Redis 2.8 引入的 PSYNC 部分重同步（第 4 章已详述）大幅缓解了"重连就要全量重传"这个根本问题；无盘复制（repl-diskless-sync） 减少了大数据集下的额外磁盘 IO。原书这两个手工缓解方案在今天依然有效（尤其是跨地域场景），但优先级应该降低——先确认 PSYNC/无盘复制配置正确，再考虑复制树或压缩隧道这类更复杂的手段。

Redis Sentinel

原书这里介绍 Sentinel 的监控机制（PUBLISH/SUBSCRIBE + PING 探测健康、多个 Sentinel 独立发现彼此和从库、故障时选举一个 Sentinel 主导切换）。这一段和第 4 章一样，写的是 Sentinel 刚成熟时的样子——今天 Sentinel 是生产级高可用的标准组件，配置文档齐全，云托管 Redis（AWS ElastiCache、阿里云 Redis 等）大多在底层用等价机制自动化了这部分工作，用户很多时候不需要自己运维 Sentinel 集群。

10.2 扩展写和内存容量

预分片（Presharding）的理念

因为分片数一旦定下来很难改（没有实时重分片能力），原书建议按未来增长预估提前多分几片——比如预计每 6 个月写入量翻 4 倍，就预先分 256 片覆盖大约 2 年的增长。这正是 Redis Cluster 用固定 16384 个哈希槽解决的问题：槽数固定不变，但槽可以在节点间迁移，不需要像本章这样"一开始就要猜对分片数量"。

10.2.1/10.2.2 手工分片基础设施

原书这里手写了一整套分片基础设施：

  • get_redis_connection()/get_sharded_connection()：从一个专门的"配置 Redis"里读 JSON 编码的连接信息（config:redis:<component>:<shard>），解析出目标分片的连接对象。
  • shard_key()：数字 key 用区间分片（int(key) // shard_size），非数字 key 用 CRC32(key) % shards 哈希分片——和第 9 章的分片 HASH 是同一个函数。
  • sharded_connection() 装饰器：自动把"key 参数"解析成对应分片的连接，注入被装饰函数。

KeyShardedConnection 与 KeyDataShardedConnection

原书封装了两个"字典下标风格"的辅助类：

  • KeyShardedConnection：conn[key] 直接返回该 key 所在分片的连接——用于只按单个 key 分片的场景（比如按用户 ID 分片的时间线）。
  • KeyDataShardedConnection：conn[id1, id2] 把两个 ID 排序后拼接成分片 key，保证"关注关系"这种需要双方数据都落在同一分片的场景，两边路由到同一台机器——这是手工版本的"哈希标签（hash tag）"。

这正是 Redis Cluster 的 {hash tag} 语法要解决的问题：Cluster 里你只需要把 key 写成 followers:{1000} 和 following:{1000}，大括号里的部分决定哈希槽，Redis 会自动保证它们落在同一个槽（同一个节点）——不需要像本章这样手写一个专门的类来"排序拼接两个 ID"。

10.3 扩展复杂查询

10.3.1 扩展搜索查询量：直接复用只读从库

第 7 章的搜索引擎用 SINTERSTORE/ZINTERSTORE 这类命令做交并集运算，这些命令本质是写命令（会把结果写入一个新 key），默认在只读从库上会报错。原书的解决办法很直接：把从库的 slave-read-only 配置成 no，允许它执行这些"写入缓存结果"的搜索命令。代价：缓存的搜索结果只存在于执行查询的那个从库上，分页请求需要"粘性路由"（同一个用户的后续请求路由到同一台从库）才能复用缓存。

10.3.2 扩展搜索索引规模：手工分片 + 客户端合并分页

这是全章技术含量最高的部分。核心难题：跨分片分页——你不知道排名第 91~100 的结果具体落在哪个分片，所以必须从每个分片都取回前 100 条，再在客户端合并重新排序，才能正确返回某一页。

原书给出两套实现，一套基于 SORT（search_get_values→get_shard_results→search_shards，用 Decimal 类型统一处理数字/字符串排序键），一套基于 ZSET（search_get_zset_values→search_shards_zset，因为分数已经是数字，合并更简单）。作者坦诚地说：分片数越多，每次查询需要拉取合并的数据量越大，到某个规模就应该考虑换成专业搜索系统（Lucene/Solr/Elasticsearch/Amazon CloudSearch）而不是继续手工优化合并逻辑。

现代视角：如果你的搜索需求已经复杂到需要跨分片合并分页，今天几乎不会继续走这条路——直接上 RediSearch（Redis Stack 自带跨分片查询能力）或 Elasticsearch/OpenSearch，这正是原书作者自己给出的建议，十年后依然成立，只是"专业搜索系统"这个选项现在也包括了 RediSearch 这种就长在 Redis 里的方案。

10.3.3 扩展社交网络：时间线按 key 分片，关注关系按数据对分片

  • 时间线（home:/profile:）：因为单条时间线数据量有限（≤1000/2000 条），不需要拆分单条时间线内部，只需要把不同用户的时间线 key 分散到不同分片——用前面的 KeyShardedConnection。
  • 关注关系（following:/followers:）：必须让关系的两端落在同一分片，才能避免"关注"操作要连两个不同分片的连接——用 KeyDataShardedConnection（排序后拼接两个用户 ID）。
  • sharded_zrangebyscore()：因为粉丝列表是按时间戳排序（而不是任意排名/偏移量），跨分片分页可以直接从"上次看到的分数"继续往下查，不需要像搜索索引那样每次都从每个分片的第 0 条重新拉取——原书明确点出这是"按分数分页"比"按排名/偏移量分页"简单得多的地方。
  • syndicate_status() 的分片版本：按目标时间线所在的分片分组，同一分片内的多个 ZADD/ZREMRANGEBYRANK 打包进一个 pipeline，减少连接数和往返次数；作者坦言这个版本可能比非分片版本"更慢"，但"这是扩展到多机所必须付出的代价"。

现代替代：直接使用 Redis Cluster

原书整章教的"presharding + CRC32 取模 + JSON 配置存储发现分片 + 客户端手工路由 + ID 对排序拼接做协同定位"，在今天绝大多数场景下应该被 Redis Cluster 取代：

原书手工方案Redis Cluster 对应能力
shard_key()（CRC32 % shards）固定 16384 个哈希槽，CRC16(key) mod 16384
分片数固定、不能重分片槽可以在节点间在线迁移，扩缩容不需要预先猜分片数
config:redis:* 手工发现分片连接集群总线（cluster bus）+ CLUSTER SLOTS/CLUSTER SHARDS，客户端自动发现拓扑
KeyDataShardedConnection 排序拼接两个 ID{hash tag} 语法：key1{tag} 和 key2{tag} 自动路由到同一个槽
客户端手工向每个分片发请求再合并跨槽的多 key 操作依然不被允许（原理相通），但单 key/hash-tag 内操作对客户端透明
Sentinel（单独运维）做主库故障切换Cluster 内置副本，槽的主节点故障后自动从副本提升

什么时候还需要走本章的手工路线：如果你的场景需要"跨分片做复杂聚合排序"（比如 10.3.2 节的搜索场景），即使上了 Redis Cluster，多 key 跨槽操作依然会被拒绝——这种情况下客户端依然需要自己实现"分别查询、本地合并"的逻辑，本章教的合并/分页技巧完全没有过时，只是"分片路由"这一层可以交给 Cluster，不用自己维护 JSON 配置。

本章小结

原书总结：只读从库、可写查询从库（slave-read-only no）、以及手工分片三件套是 2013 年扩展 Redis 的全部武器库。现代读者应该把"手工分片"这部分理解为"Redis Cluster 出现之前的历史必然"——理解它能帮你理解 Cluster 解决了什么问题、什么时候 Cluster 也无能为力（跨槽多 key 聚合）需要你自己在应用层继续做本章教的"分别查询+合并"。
