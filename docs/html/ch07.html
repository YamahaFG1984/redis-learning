第 7 章

第 7 章 基于搜索的应用

对应原书第 7 章 "Search-based applications"，讲了四件事：Redis 里搜索、给搜索结果排序、广告投放、职位搜索。核心手法是用 SET/ZSET 的交并差运算模拟倒排索引和打分系统。

说明：原书目录里"电商市场"相关内容其实在第 4/6 章（list_item/purchase_item），第 7 章本身并没有独立的市场章节，这里只整理第 7 章实际包含的四个主题。

7.1 在 Redis 里搜索

倒排索引基础

分词（提取字母组成、长度≥2 的词）→去停用词→把每个词映射成一个 SET（ind:<word> → 包含该词的文档 ID 集合）。多词 AND 查询用 SINTER，同义词 OR 查询用 SUNION，排除词用 SDIFF。原书定义了一个简单的查询语法：词前面加 + 表示"是前一个词的同义词"（先分组做并集，再参与最终交集），加 - 表示排除。

现代视角：这一整套"手写倒排索引"的方法，在今天几乎完全可以被 RediSearch（现已作为 FT.* 命令族合入 Redis Stack/Redis 8）替代——FT.CREATE 建索引、FT.SEARCH/FT.AGGREGATE 直接支持全文检索、数值范围、地理位置、向量检索、聚合排序，语法上远比手写 SINTER/SUNION 表达力强，性能也是原生 C 实现。如果你在 2020 年之后开始一个新项目需要全文搜索，直接用 RediSearch，而不是重新实现本章的手工方案——但理解手工方案的原理，能帮你理解 RediSearch 内部到底在做什么，以及什么时候手写方案反而更合适（比如极简单的标签过滤，不需要引入整个模块）。

SORT 排序结果

用 SORT 引用外部 HASH 字段做排序（BY kb:doc:*->updated），结果集给一个 TTL 做分页缓存。原书点出这个方案的局限——SORT 只能按单一标准排序，这就引出了下一节。

7.2 用 ZSET 做排序索引

组合排序：不预先固定权重

核心技巧：SET 可以直接作为 ZINTERSTORE/ZUNIONSTORE 的输入参数，Redis 把 SET 的每个成员当作分数为 1 的 ZSET 处理。这样可以把"搜索结果 SET"、"更新时间 ZSET"、"投票数 ZSET"用可调节的权重实时组合，而不需要像第 1 章那样把"每票等于多少分"写死在数据写入时。

非数值排序：字符串转分数

ZSET 分数必须是浮点数，但有时候想按字符串排序（比如按用户名字典序）。原书的技巧：取字符串前 6 个字符，ord() 转数字，用 257 为进制组合成一个数（用 257 而不是 256，是为了给"短字符串填充位"留出区别于"内嵌 null 字节"的空间），最后再乘 2 加一位标志"字符串是否超过 6 个字符"——大约用满 IEEE 754 双精度浮点数的 49 个比特位。

局限：字符串转的分数只能定义一种排序顺序，不能像数值分数那样和别的分数相加组合（比如不能"字符串排序权重 + 热度权重"）。

现代视角：字符串转分数这个技巧本身没有过时（IEEE 754 浮点数精度限制没有变），但如果你需要"按字典序做范围查询"，Redis 早就有更直接的官方命令——ZRANGEBYLEX/ZREVRANGEBYLEX（Redis 2.8.9 起，原书写作时刚发布不久，未收录进本书），专门用来对"所有成员分数相同"的 ZSET 做字典序范围查询，不需要再手工做字符串到数值的转换。第 6 章的公会自动补全场景，用 ZRANGEBYLEX 实现会比原书的"插入哨兵 + WATCH"方案简单得多——这是原书出版后 Redis 官方"追上"手工技巧的一个好例子。

7.3 广告投放

这一节作者说是基于自己"实际在生产环境跑过几个月的软件"整理的，含金量很高，是全书最贴近真实工业系统的一节。

三种计价模式统一成 eCPM

  • CPM（千次曝光计费）：eCPM = CPM。
  • CPC（点击计费）：eCPM = 1000 × CPC × 点击率。
  • CPA（转化计费）：eCPM = 1000 × 点击率 × 转化率 × 单次转化价值。

原始的曝光/点击/转化次数都被完整保存（而不是只存点击率），这样 eCPM 可以随时重新计算。

索引与投放

index_ad()：把广告加入地域 SET、内容词 ZSET，用系统平均点击率给冷启动广告一个初始 eCPM 估计。target_ads() 的核心流程：地域匹配（union 多个地域 SET 再和全局 eCPM ZSET 相交）→ 内容词加成（每个匹配词都有一个"该词的 eCPM 加成"ZSET）→ 取 eCPM 最高的广告 → 记录本次投放用于学习。

"数学上不算严谨"的加成算法（原书自己在侧栏承认）：多个匹配词的加成不能简单相加，但严格算加权平均又做不到（ZSET 之间不能相除），于是采用"取所有匹配词加成的最小值和最大值，各取一半平均"这种权宜之计。作者原话："我选这个方法是因为它好写、好懂、好改进"——这是一个很坦诚的工程态度：不追求完美算法，先让系统跑起来，用数据反馈迭代。

从用户行为里学习

record_targeting_result()/record_click()/update_cpms() 三兄弟：记录曝光/点击/转化 → 定期（每 100 次曝光，或每次点击/转化）重新计算 eCPM 和每个词的加成值。原书结尾列了一串没有实现、但明确指出方向的改进点，这些建议放到今天依然是广告系统/推荐系统的入门必修课：

  • 按时间衰减旧数据（老点击率不该永远占权重）。
  • 多时间窗口（天/周）加权。
  • 二价拍卖（按第二高出价收费，真实广告网络的标准做法）。
  • 探索与利用（exploration vs exploitation）：不要总是展示 eCPM 最高的广告，否则新广告永远拿不到曝光数据来学习——建议在 Top 100 广告里 10%~50% 的流量做随机采样。这正是多臂老虎机（multi-armed bandit）问题的雏形，现代做法通常直接用 Thompson Sampling 或 UCB 算法。
  • 冷启动：把全局平均点击率和广告自己的观测点击率按曝光数加权混合，2,000~5,000 次曝光通常足够得到可信的点击率估计。
  • 建议把记录曝光/点击这类写操作放到后台异步任务里，不要阻塞广告投放的主流程（复用第 6 章的任务队列思路）。

现代视角：这套"手写 eCPM + ZSET 加成"的广告系统，今天大型广告平台早已升级为基于机器学习的实时竞价系统（在线学习模型、特征工程流水线、向量检索做内容匹配）。但对于中小型系统（站内广告位、优惠券推荐、内容置顶竞价），本章的方法论依然是一个性价比很高的起点——它不需要机器学习基础设施，纯用 Redis 数据结构就能做到"有反馈闭环的排序系统"，这是很多创业公司实际会走的第一步。如果要往前演进，下一步通常是引入向量检索（Redis 8 的 VSIM/RediSearch 的向量字段）做内容/用户的语义匹配，或者接入专门的特征存储（Feast 等）。

7.4 职位搜索

朴素方案的局限

每个职位一个 SET（存所需技能），要判断候选人是否满足，把候选人技能放进一个临时 SET 求 SDIFF，为空则合格。原书明确说这个方案"没法扩展到查一个候选人能匹配所有职位"，因为要挨个检查每个职位。

反过来做（和广告投放的内容加成是同一个技巧）

把索引方向倒过来：每个技能一个 SET（存需要它的职位 ID），另一个 ZSET jobs:req 记录每个职位总共需要多少技能。查询时：ZUNIONSTORE 候选人拥有的技能对应的 SET，得到"每个职位匹配了几项技能"；再和 jobs:req 做 ZINTERSTORE（权重 -1 和 1），"匹配技能数 - 所需技能数 = 0" 的职位就是完全匹配的。

这是本章方法论上最有启发性的一课：当"从 A 找 B"扩展性不好的时候，试着把索引方向倒过来，从"B 的每个属性值"反向索引出"哪些 A 有这个值"——这正是搜索引擎倒排索引的核心思想，原书用广告投放（词→广告）和职位搜索（技能→职位）两个场景反复演练了这同一个模式。

本章小结

原书这一章的核心结论：Redis 的少量数据结构（加上 pub/sub）本身就是一个完整的工具箱，能撑起搜索、排序、广告投放、职位匹配这些看起来需要"专业中间件"的系统。现代视角的更新是：如果搜索/排序需求变复杂（全文相关性、向量语义匹配、大规模聚合），优先考虑 RediSearch/Redis Stack 而不是继续手写 SINTER/ZINTERSTORE 拼接方案；但广告投放这类"打分 + 反馈学习"的系统，本章的方法论至今仍是很多实际项目的合理起点。
