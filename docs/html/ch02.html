Redis in Action 现代化笔记 第 2 章

本页目录

    第 2 章 剖析一个 Redis Web 应用

    对应原书 Redis in Action 第 2 章 "Anatomy of a Redis web application"。原书基于 Redis 2.6 + Python 2.x 讲解，本文在忠实还原原书设计思路的基础上，补充了现代 Redis（7.x/8.x）的等价做法、生产实践经验，并给出 Python / Java / TypeScript 三语言示例（Web 框架以 Django、Hono.js 为例）。

    2.0 背景：一个虚构的电商站点

    原书用一个虚构案例 "Fake Web Retailer" 贯穿全章：日均 PV 约 1 亿，日活约 500 万，日销 10 万+ 件商品。作者给出了一个关键性的工程判断，这个判断在今天依然成立：

    关系型数据库单机大约只能扛住 200~2,000 次/秒的行级写入（insert/update/delete），批量写入更快，但页面级的零散写入用不上批量优化。

    这一章要解决的都是"关系型数据库扛不住，但 Redis 天然适合"的场景：登录会话、购物车、页面缓存、行缓存、访问分析。这五个场景有一个共同点——都是高频、低价值密度的读写，用内存结构 + 简单命令就能解决，没必要占用关系型数据库的连接和 IO。这个判断标准放到今天依然是选择 Redis 的核心理由。

    2.1 登录与 Cookie 缓存

    设计取舍：签名 Cookie vs Token Cookie

    原书对比了两种会话方案：

    方案优点缺点
    签名 Cookie（内容+签名都放 Cookie）无需服务端存储，验证自包含签名逻辑容易写错，一旦签发/校验疏漏就是安全漏洞
    Token Cookie（Cookie 只放随机 token，服务端存 token→用户的映射）Cookie 体积小（移动端/弱网友好），易扩展字段需要服务端存储；如果这个存储是关系型数据库，读写代价高

    Fake Web Retailer 选择 Token Cookie，把"token→用户"这张表从关系型数据库搬到 Redis 的 HASH 里：

    login:<token>  →  HASH { }  # 简化为直接存 username 字符串
recent:        →  ZSET { token: 最近访问时间戳 }
viewed:<token> →  ZSET { item_id: 浏览顺序 }，只保留最近 25 个

    核心函数（对应原书 Listing 2.1 / 2.2）：

    • check_token()：HGET login: token 取用户名。
    • update_token()：每次页面访问都调用——更新 login: 里的 token→user、刷新 recent: 里该 token 的时间戳、如果本次浏览了商品则把商品 ID 塞进 viewed:<token> 并裁剪到最近 25 条。

    原书数据：这套方案可以做到 ≥2 万次商品浏览记录/秒，是关系型数据库方案的 10~100 倍。

    清理策略：为什么不直接用 EXPIRE

    原书刻意没有用 EXPIRE 来自动过期会话，而是维护一个 recent: ZSET（按最后访问时间排序）+ 一个后台清理循环 clean_sessions()：当 ZCARD recent: 超过阈值（书中设为 1000 万），就用 ZRANGE 取出最老的一批 token，依次删除 login:、viewed:<token>、recent: 里的对应条目。

    作者明确解释了为什么不用 EXPIRE：

    1. 需要一个显式的总量上限（比如"最多保留 1000 万活跃会话"），而 EXPIRE 只能控制单个 key 的存活时间，做不到"超过总量就淘汰最老的"。
    2. 为将来的"购物车放弃"分析留口子——如果用 EXPIRE 自动删除，就没有机会在删除前对这些即将过期的会话做业务分析。

    作者也坦诚地指出这里存在一个竞态条件：清理循环可能恰好在用户访问的同一时刻删除了他的会话。他的态度是——这个概率极低，即使发生，最坏结果只是用户被迫重新登录，不值得为此引入额外的加锁开销（第 3、4 章会讲真正的并发控制手段）。

    给现代读者的启示：这个"要不要为极小概率的竞态加锁"的权衡思路，在今天做缓存/会话系统设计时依然通用——先问"最坏情况的业务代价是什么"，再决定要不要加锁，不要无脑加锁。

    现代 Redis 怎么做会做得更好

    原书这套"ZSET + 轮询清理线程"的方案是 2013 年的工程妥协，今天有更省心的替代方案：

    • 直接用 EXPIRE/SET ... EX 做会话 TTL：如果业务不需要"精确总量上限"和"过期前分析"，现代做法就是给 login:<token> 设置滑动过期时间（每次访问 EXPIRE 续期），完全不需要自己写清理循环。Redis 的过期是惰性删除 + 定期主动扫描结合的，不会有内存泄漏问题。
    • 如果确实需要"总量上限 + 过期前钩子"：可以用 keyspace notification（notify-keyspace-events Ex）订阅 expired 事件，在真正过期时触发分析逻辑，而不必自己维护一个轮询线程去猜"谁该被清理"。
    • Redis 7.4+ 的 Hash Field Expire（HEXPIRE/HPEXPIRE/HTTL/HPERSIST）：允许给 HASH 里的单个字段设置 TTL。如果把会话建模成一个大 HASH（sessions 这个 key 下面每个 field 是一个 token），现在可以直接对 field 级别做过期，不再需要额外的 recent: ZSET 来模拟"哪些 token 该清理"。这是这几年 Redis 在这个具体场景下最大的能力补齐。
    • 生产实践：会话存储更推荐直接用现成的 session 中间件（Django 的 django-redis session backend、Node 生态的 connect-redis），而不是手写 token→user 的 HASH 逻辑，除非你需要书中这种"顺带记录最近浏览"的定制行为。

    代码示例

    Python（redis-py，现代写法）

    import time
import redis

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

SESSION_TTL = 30 * 60  # 30 分钟滑动过期

def check_token(token: str) -> str | None:
    return r.get(f"login:{token}")

def update_token(token: str, user: str, item: str | None = None):
    pipe = r.pipeline()
    pipe.set(f"login:{token}", user, ex=SESSION_TTL)  # 现代 SET 自带 EX，替代 SETEX
    if item:
        key = f"viewed:{token}"
        pipe.zadd(key, {item: time.time()})            # 现代 zadd 用 mapping，而非位置参数
        pipe.zremrangebyrank(key, 0, -26)               # 只保留最近 25 条
        pipe.expire(key, SESSION_TTL)
        pipe.zincrby("viewed:", -1, item)               # 全局热度榜，负分实现"最热在前"
    pipe.execute()

    对比原书代码：原书 conn.zadd('recent:', token, timestamp) 是老版本 redis-py 的位置参数写法；现代 redis-py（4.x/5.x）zadd 统一要求传 {member: score} 字典。conn.setex(key, value, seconds) 这种参数顺序在现代客户端里也变成了 set(key, value, ex=seconds) 或 setex(key, seconds, value)——参数顺序刚好相反，照抄原书代码在新版客户端上会直接出错，这是升级迁移时最容易踩的坑。

    Java（Jedis 5.x）

    import redis.clients.jedis.UnifiedJedis;
import redis.clients.jedis.params.SetParams;

public class SessionStore {
    private final UnifiedJedis jedis;
    private static final long SESSION_TTL = 30 * 60; // 秒

    public SessionStore(UnifiedJedis jedis) {
        this.jedis = jedis;
    }

    public String checkToken(String token) {
        return jedis.get("login:" + token);
    }

    public void updateToken(String token, String user, String item) {
        jedis.set("login:" + token, user, new SetParams().ex(SESSION_TTL));
        if (item != null) {
            String key = "viewed:" + token;
            jedis.zadd(key, System.currentTimeMillis() / 1000.0, item);
            jedis.zremrangeByRank(key, 0, -26);
            jedis.expire(key, SESSION_TTL);
            jedis.zincrby("viewed:", -1, item);
        }
    }
}

    TypeScript（ioredis + Hono.js）

    // session.ts
import { Redis } from "ioredis";

const redis = new Redis();
const SESSION_TTL = 30 * 60;

export async function checkToken(token: string) {
  return redis.get(`login:${token}`);
}

export async function updateToken(token: string, user: string, item?: string) {
  const pipe = redis.pipeline();
  pipe.set(`login:${token}`, user, "EX", SESSION_TTL);
  if (item) {
    const key = `viewed:${token}`;
    pipe.zadd(key, Date.now() / 1000, item);
    pipe.zremrangebyrank(key, 0, -26);
    pipe.expire(key, SESSION_TTL);
    pipe.zincrby("viewed:", -1, item);
  }
  await pipe.exec();
}

    // app.ts — Hono.js 中间件，从 Cookie 里取 token 并续期会话
import { Hono } from "hono";
import { getCookie, setCookie } from "hono/cookie";
import { checkToken, updateToken } from "./session";
import { randomUUID } from "crypto";

const app = new Hono();

app.use("*", async (c, next) => {
  let token = getCookie(c, "token");
  if (!token) {
    token = randomUUID();
    setCookie(c, "token", token, { httpOnly: true, maxAge: 30 * 60 });
  }
  const user = await checkToken(token);
  c.set("user", user);
  c.set("token", token);
  await next();
  await updateToken(token, user ?? "anonymous"); // 请求结束后续期
});

export default app;

    2.2 购物车

    原书的关键洞察是：购物车没必要单独设计存储方案，直接复用登录会话的 token 当 key。购物车是一个 cart:<token> 的 HASH，field 是商品 ID，value 是数量：

    def add_to_cart(token: str, item: str, count: int):
    key = f"cart:{token}"
    if count <= 0:
        r.hdel(key, item)          # 原书代码写的是 conn.hrem(...)，hrem 并不是真实存在的 Redis/redis-py 命令名，
                                    # 这是原书代码里的一个笔误，真正应该调用的是 HDEL / hdel
    else:
        r.hset(key, item, count)

    踩坑提醒：原书 Listing 2.4 无论是书里印刷的文字还是配套源码，都写的是 conn.hrem(...)。这在 redis-py（不论新旧版本）里都不是一个真实存在的方法名——正确的命令是 HDEL。如果你直接复制原书代码会得到 AttributeError，这是原书本身的错误，不是版本变迁导致的。

    现代做法上，购物车通常直接给 cart:<token> 这个 key 设置和会话一致的 TTL（EXPIRE），会话过期购物车自然消失，不需要原书里"清理会话时顺带删购物车"的额外逻辑（clean_full_sessions()）。

    作者也提到一个当年没做但值得记住的方向：既然 session 和 cart 都在 Redis 里，天然适合做"浏览了 A 最终购买 A 的转化率""买了 A 的人还买了 B"这类推荐分析——这正是后面电商推荐系统、实时特征存储的雏形。

    2.3 页面缓存

    场景：95% 的页面一天最多变化一次，没必要每次请求都重新渲染。方案是标准的 cache-aside：

    def cache_request(request, callback):
    if not can_cache(request):
        return callback(request)
    key = "cache:" + hash_request(request)
    content = r.get(key)
    if content is None:
        content = callback(request)
        r.setex(key, 300, content)   # 5 分钟 TTL
    return content

    原书数据：把一个 20~50ms 的动态渲染页面，换成一次 Redis 往返（本地 <1ms，同机房 <5ms）。这个思路今天完全没变，唯一要补的是两个 2013 年还不常讨论、但现在是标配的问题：

    • 缓存击穿/惊群（cache stampede）：如果一个热点 key 恰好过期，同一瞬间可能有几百个请求同时穿透到后端重新计算。现代做法是加互斥锁（第 6 章会讲 Redis 分布式锁）或用 概率性提前刷新（probabilistic early expiration，如 XFetch 算法），而不是像原书那样让所有并发请求都直接穿透。
    • 缓存版本化/软删除：直接 DEL 缓存 key 容易在高并发下和"重新写入"竞争，现代实践更倾向于给缓存 value 加时间戳/版本号，用"写入新版本"代替"删除旧版本"。

    2.4 数据库行缓存

    场景：秒杀页面需要展示"剩余库存"这种强时效数据，整页缓存会导致库存数字错误，但每次都查数据库又扛不住。方案是用一个后台常驻进程，按不同商品各自的更新频率，把数据库的行以 JSON 字符串形式缓存进 Redis：

    schedule:  ZSET { row_id: 下次应该刷新的时间戳 }
delay:     ZSET { row_id: 刷新间隔秒数（≤0 表示应该停止缓存并清除） }
inv:<id>   STRING  JSON 序列化的行数据

    cache_rows() 是一个死循环：每次从 schedule: 取分数最小（最快到期）的一条，判断是否到期，到期就重新查库、写回 inv:<id>、按 delay: 里的间隔重新计算下次调度时间；如果 delay ≤ 0 就把这一行从两个 ZSET 中移除并删除缓存，相当于"取消缓存"。

    原书专门用一个侧栏讨论了"为什么用 JSON 而不是 Protobuf/Thrift/BSON/MessagePack"——作者的答案很诚实：这只是个人偏好（可读性 + 几乎所有语言都有现成库），并且明确说"你想换别的格式完全没问题"。另一个侧栏讲了 Redis 不支持嵌套结构（HASH 里不能塞 ZSET）这个设计取舍：作者的类比是"如果 HASH 里嵌套了 5 层，你怎么对最深层的一个值做 INCR？"——保持命令语义简单是 Redis 的设计哲学，解决办法要么是用 key 命名约定（user:123 是 HASH，user:123:posts 是独立的 ZSET），要么是应用层自己序列化。这个设计哲学到今天完全没变——RedisJSON（现已合入 Redis 8 的 JSON.* 命令族）某种程度上就是在回应这个多年的诉求，但核心 KV/结构化命令的语义仍然保持扁平。

    现代等价方案：这种"定时轮询数据库同步到缓存"的模式，今天更常见的实现是：

    • 用 CDC（Change Data Capture，如 Debezium 监听 MySQL/Postgres binlog） 把行变更实时推到 Redis，而不是自己写轮询调度器猜"多久该刷新一次"。
    • 库存这种强一致性要求的场景，现在业界更倾向于库存直接放在 Redis 里做原子扣减（DECRBY / Lua 脚本），数据库作为异步落盘的最终存储，而不是反过来"数据库为主、Redis 为缓存"。这是本章思路的一个重要延伸，第 6、11 章会涉及原子操作和 Lua 脚本。

    2.5 网页访问分析

    场景延续：Fake Web Retailer 把 10 万个商品页全部缓存，缓存撑爆了内存，只能容纳约 1 万个页面。于是需要"只缓存最热门的页面"。

    做法是复用 update_token() 里已经记录的浏览数据，追加一行：

    r.zincrby("viewed:", -1, item)   # 分数取负数，让"看得最多的"排在 ZRANGE 最前面（rank 0）

    为了不让这个全局热度榜无限增长、也让新商品有机会追上来，rescale_viewed() 每 5 分钟做一次：

    1. ZREMRANGEBYRANK viewed: 20000 -1——只留 Top 2 万。
    2. 用 ZINTERSTORE（权重设为 0.5，对 viewed: 和自身求交集）把所有分数减半——这是一个很巧妙的技巧：ZINTERSTORE 可以在合并多个 ZSET 时，对每个输入分别乘一个权重，这里用"自己和自己相交、权重 0.5"来实现"整体分数减半"，避免了新写一个命令来做批量数值变换。

    can_cache() 最终的判断逻辑：请求里能提取出商品 ID、且不是动态请求、且该商品在 viewed: 里的 ZRANK < 10000，才允许缓存。

    现代视角：ZINCRBY/ZRANK 做热度排行榜这个模式至今仍是 Redis 排行榜类应用的标准做法，几乎没有过时。如果热度统计的量级进一步上升（比如要统计"独立访客数"而不是"浏览次数"），现代 Redis 会推荐引入 HyperLogLog（PFADD/PFCOUNT） 做基数估算，或者用 RedisTimeSeries 模块做带时间窗口的统计——这些都是 2013 年之后才出现、原书完全没有涉及的能力，值得在真实项目里替换掉手写的"定时减半"轮询逻辑。

    2.7 本章小结（原书 + 现代补充）

    本章小结

    原书的收尾提醒是：不要害怕在早期代码基础上叠加新需求——购物车和访问分析都是直接复用登录会话这一份数据结构演化出来的，而不是重新设计。这是一个很朴素但常被忽视的工程建议。

    补充给现代读者的清单：

    1. 会话/购物车 TTL 优先用原生 EXPIRE/SET EX，只有在需要"硬性总量上限"或"过期前钩子"时才考虑 keyspace notification 或应用层调度。
    2. 页面/行缓存要考虑缓存击穿保护（锁或概率early expiration），原书没讨论这个问题是因为 2013 年这还不是主流话题。
    3. 数据库行缓存这种"轮询同步"模式，能用 CDC 替代的就不要自己写调度器。
    4. 热度排行榜（ZINCRBY + ZRANK）模式基本没有过时，但基数类统计（去重计数）现在应该用 HyperLogLog，而不是复用浏览次数榜单。
