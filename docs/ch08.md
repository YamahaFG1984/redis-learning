# 第 8 章 构建一个简单的社交网络

> 对应原书第 8 章 "Building a simple social network"，用 Redis 实现了 Twitter 后端的核心功能：用户/状态、主页时间线、关注关系、发帖/删帖的扇出策略、流式 API。原书明确说这一章"不追求 Twitter 那种规模，但足以教会你怎么用简单结构搭建社交网络的核心"。

## 8.0 设计原则：尽量减少"查看时"的计算

原书开篇就点明和第 7 章的差异：第 7 章的广告/搜索是查询密集型，这一章的社交网络要反过来——**优先做"写入时多算一点，查看时几乎不算"（fan-out on write），而不是"写入时什么都不做，查看时现算"（fan-out on read）**。这是社交网络系统设计里最经典的权衡，至今没有变过（Twitter/Weibo 内部架构公开资料里都反复提到同样的取舍）。

## 8.1 用户与状态

- `user:<id>` HASH：`login`/`id`/`name`/`followers`/`following`/`posts`/`signup`。
- `users:` HASH：登录名（小写）→ 用户 ID，防止重名。
- `create_user()` 用第 6 章的锁（`acquire_lock_with_timeout`）保护"检查登录名是否被占用 + 创建用户"这两步，防止并发注册撞名。
- **敏感信息不进这个 HASH**：原书专门用侧栏强调——密码哈希、邮箱这类敏感数据不应该放进这个被频繁整体读取（渲染模板、API 响应）的 HASH，应该存在别处。这是一个至今非常重要的安全设计原则。
- `status:<id>` HASH：消息内容、发布时间、发帖人 ID **和登录名**（登录名冗余存一份，省得渲染时间线时再查一次用户表）——**反规范化换查询性能**，社交网络系统里几乎无处不在的权衡。

## 8.2 主页时间线

`home:<uid>` ZSET，member=状态 ID，score=发布时间戳。读取时先 `ZREVRANGE` 拿到一页状态 ID，再逐个 `HGETALL`（原书用 `filter(None, ...)` 优雅地跳过已经被删除的状态——**这是"删除时不用费心清理所有引用，读取时自然过滤掉"设计的关键前提**，8.4 节会展开讲）。同一个函数通过 `timeline` 参数复用给"主页时间线"（`home:`）和"个人主页时间线"（`profile:`）两种场景。

## 8.3 关注/粉丝列表

`following:<uid>` 和 `followers:<uid>` 是同一个关系的两个视角，都是 ZSET（member=对方 ID，score=关注时间戳）。

`follow_user()` 除了双向写入这两个 ZSET，还会做一件很关键的事：**把被关注者最近的 1000 条帖子直接拉进新粉丝的主页时间线**（`ZREVRANGE` 取被关注者的 `profile:` 时间线，`ZADD` 灌进粉丝的 `home:`，再裁剪到 1000 条上限）——这样新粉丝关注后立刻就能看到对方的历史内容，而不用等对方下一次发帖。取消关注是镜像操作，还要把对方的帖子从自己主页时间线里移除。

## 8.4 发帖与删帖：处理"大 V"问题

### 为什么不能无脑同步扇出

原书用 Twitter 真实的粉丝分布数据来论证设计取舍：全平台粉丝数超过 1000 的用户只占约 **0.1%**，也就是说**同步扇出到前 1000 个粉丝，能覆盖 99.9%+ 的发帖场景**；剩下 0.1% 的大 V（粉丝数可能到几百万甚至 2500 万）如果也同步扇出会让请求响应时间无法接受。

`syndicate_status()` 的设计：每次处理 1000 个粉丝（`POSTS_PER_PASS`），如果这一批刚好取满 1000（意味着可能还有更多），就通过第 6 章的延迟任务机制（`execute_later()`）把"继续处理剩下的粉丝"安排到后台，不阻塞发帖请求本身。**这是 fan-out-on-write 模式在真实系统里必须解决的核心难题**——纯同步扇出扛不住大 V，纯异步扇出又会让普通用户的关注者看到延迟的内容，原书这里选择了"前 1000 个同步、其余异步"的混合策略。

### 删帖为什么"很简单"

因为读取路径（`get_status_messages()`）本来就会自动过滤已删除的状态（`HGETALL` 一个不存在的 key 返回空），所以删帖只需要 `DEL` 状态 HASH 本身——清理各处时间线里残留的 ID **"不是严格必要的，只是让时间线看起来干净一点"**。原书特意留了一道练习题指出：这个简化处理会在每个粉丝的主页时间线里留下"僵尸 ID"，需要专门的清理逻辑（源码里有 `clean_timelines()` 作为练习答案）。

## 8.5 流式 API

原书用 HTTP **分块传输编码（chunked transfer encoding）** 自己搭了一个流式推送服务，明确提到当时 WebSocket/SPDY 的客户端支持还不成熟，所以选择了更朴素的 chunked HTTP。核心机制：

- `create_status()`/`delete_status()` 在写入的同时 `PUBLISH` 到 `streaming:status:` 频道。
- 删帖发布的是"标记为已删除"的完整消息，而不只是一个 ID——原书解释这样做的好处：**删除通知复用和原发布消息完全相同的过滤逻辑**，服务端不需要额外记录"这个客户端之前收到过哪些消息"，省内存也简化了实现。
- 几种过滤器（`SampleFilter`/`TrackFilter`/`FollowFilter`/`LocationFilter`）模拟了 Twitter 真实的流式 API（firehose/gardenhose/spritzer 采样、关键词、关注列表、地理位置边界框过滤）。`SampleFilter` 用客户端 ID 作随机种子，保证同一个客户端断线重连后依然采样到同一批 ID 子集——这样即使断线重连，只要重连发生在删除通知到达之前，客户端依然能收到匹配的删除通知。

**现代视角**：这套"手写 HTTP chunked 流式服务器 + pub/sub 分发"的方案，在今天几乎不会这么做了：

- **WebSocket 和 Server-Sent Events (SSE)** 现在客户端支持非常成熟，是流式推送的标准选择，不再需要 chunked encoding 这种变通方案。
- **推送的可靠性问题**：原书用 pub/sub 做频道分发，断线会丢消息（第 3 章已经讨论过 pub/sub 的固有局限）——如果今天要做"可回放"的流式 API，应该用 **Redis Streams**，客户端可以带着上次读到的位置重连，不会丢失断线期间的消息。
- 大规模实时推送（真正到 Twitter 规模）今天通常会用专门的实时消息基础设施（Kafka + WebSocket 网关、Pusher/Ably 这类托管服务），Redis pub/sub 更适合中小规模场景。

## 现代示例：核心发帖/关注/时间线读取（三语言）

**Python（redis-py）**

```python
import time, uuid
import redis

r = redis.Redis(decode_responses=True)
HOME_TIMELINE_SIZE = 1000

def follow_user(uid: str, other_uid: str):
    fkey1 = f"following:{uid}"
    fkey2 = f"followers:{other_uid}"
    if r.zscore(fkey1, other_uid) is not None:
        return None
    now = time.time()
    pipe = r.pipeline(True)
    pipe.zadd(fkey1, {other_uid: now})
    pipe.zadd(fkey2, {uid: now})
    pipe.zrevrange(f"profile:{other_uid}", 0, HOME_TIMELINE_SIZE - 1, withscores=True)
    following, followers, statuses = pipe.execute()[-1:] + [None, None]  # 简化示意
    # 把最近的帖子灌入新粉丝的主页时间线
    recent = r.zrevrange(f"profile:{other_uid}", 0, HOME_TIMELINE_SIZE - 1, withscores=True)
    if recent:
        pipe = r.pipeline(True)
        pipe.zadd(f"home:{uid}", dict(recent))
        pipe.zremrangebyrank(f"home:{uid}", 0, -HOME_TIMELINE_SIZE - 1)
        pipe.execute()
    return True

def post_status(uid: str, message: str) -> str:
    posted = time.time()
    status_id = str(r.incr("status:id:"))
    login = r.hget(f"user:{uid}", "login")
    r.hset(f"status:{status_id}", mapping={
        "message": message, "posted": posted, "id": status_id,
        "uid": uid, "login": login,
    })
    r.hincrby(f"user:{uid}", "posts", 1)
    r.zadd(f"profile:{uid}", {status_id: posted})
    syndicate_status(uid, status_id, posted)
    return status_id

def syndicate_status(uid: str, status_id: str, posted: float, start: int = 0):
    followers = r.zrangebyscore(f"followers:{uid}", start, "+inf", start=0, num=1000, withscores=True)
    pipe = r.pipeline(True)
    for follower, score in followers:
        pipe.zadd(f"home:{follower}", {status_id: posted})
        pipe.zremrangebyrank(f"home:{follower}", 0, -HOME_TIMELINE_SIZE - 1)
    pipe.execute()
    if len(followers) >= 1000:
        # 大 V 场景：剩余粉丝交给后台任务继续处理（第 6 章 execute_later 思路）
```

**Java（Jedis）**

```java
public String postStatus(UnifiedJedis jedis, String uid, String message) {
    double posted = System.currentTimeMillis() / 1000.0;
    String statusId = String.valueOf(jedis.incr("status:id:"));
    String login = jedis.hget("user:" + uid, "login");

    Map<String, String> fields = Map.of(
        "message", message, "posted", String.valueOf(posted),
        "id", statusId, "uid", uid, "login", login);
    jedis.hset("status:" + statusId, fields);
    jedis.hincrBy("user:" + uid, "posts", 1);
    jedis.zadd("profile:" + uid, posted, statusId);

    syndicateStatus(jedis, uid, statusId, posted);
    return statusId;
}

public void syndicateStatus(UnifiedJedis jedis, String uid, String statusId, double posted) {
    List<String> followers = jedis.zrangeByScore("followers:" + uid, 0, Double.POSITIVE_INFINITY, 0, 1000);
    Pipeline pipe = jedis.pipelined();
    for (String follower : followers) {
        pipe.zadd("home:" + follower, posted, statusId);
        pipe.zremrangeByRank("home:" + follower, 0, -1001);
    }
    pipe.sync();
}
```

**TypeScript（ioredis + Hono.js 发帖接口）**

```ts
import { Hono } from "hono";
import { Redis } from "ioredis";

const redis = new Redis();
const HOME_TIMELINE_SIZE = 1000;

async function postStatus(uid: string, message: string) {
  const posted = Date.now() / 1000;
  const statusId = String(await redis.incr("status:id:"));
  const login = await redis.hget(`user:${uid}`, "login");

  await redis.hset(`status:${statusId}`, {
    message, posted, id: statusId, uid, login,
  });
  await redis.hincrby(`user:${uid}`, "posts", 1);
  await redis.zadd(`profile:${uid}`, posted, statusId);

  await syndicateStatus(uid, statusId, posted);
  return statusId;
}

async function syndicateStatus(uid: string, statusId: string, posted: number) {
  const followers = await redis.zrangebyscore(`followers:${uid}`, 0, "+inf", "LIMIT", 0, 1000);
  const pipe = redis.pipeline();
  for (const follower of followers) {
    pipe.zadd(`home:${follower}`, posted, statusId);
    pipe.zremrangebyrank(`home:${follower}`, 0, -HOME_TIMELINE_SIZE - 1);
  }
  await pipe.exec();
}

const app = new Hono();
app.post("/status", async (c) => {
  const { uid, message } = await c.req.json();
  const statusId = await postStatus(uid, message);
  return c.json({ statusId });
});

export default app;
```

## 本章小结

原书这套"HASH 存实体 + ZSET 做时间线/关系 + 同步扇出前 N 个粉丝、其余异步"的设计，至今仍是理解真实社交网络系统架构的最佳教学案例——公开资料显示 Twitter/微博内部的时间线服务本质上就是这个模式的工业级实现（加上更复杂的缓存分层和降级策略）。**现代补充**：流式 API 部分建议直接上 WebSocket/SSE + Redis Streams，而不是重造 chunked HTTP 服务器；如果时间线规模进一步增长到单机撑不住，第 10 章会讲怎么把这里的 ZSET 结构分片到多台机器。
