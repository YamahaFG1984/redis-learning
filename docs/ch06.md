# 第 6 章 用 Redis 构建应用组件

> 对应原书第 6 章 "Application components in Redis"，原书最长的一章，讲了自动补全、分布式锁、计数信号量、任务队列、可靠消息投递、文件分发六大主题。这一章教的很多"手工组件"在今天有了官方原语（尤其是 Redis Streams），但理解手工实现的原理，能帮你更好地理解官方方案到底解决了什么问题。

## 6.1 自动补全

### 最近联系人（LIST 方案）

`recent:<user>` 是一个 LIST，每次联系某人：`LREM` 删除旧记录 → `LPUSH` 插到最前 → `LTRIM` 裁到 100 条，包在 `MULTI/EXEC` 里保证原子性。查询时整条 `LRANGE` 取出来，**客户端本地**做前缀过滤——Redis 本身不负责模糊匹配。

原书明确指出局限：`LREM` 是 O(列表长度)，只有在列表被裁剪到 100 条这种小规模下才可接受，规模更大时应该换成 ZSET + 时间戳。

### 公会/群组自动补全（ZSET range 技巧）

这是本章最精巧的技巧之一：把 ZSET 所有成员的分数都设成 0，ZSET 就退化成按**字典序**排列。要查前缀 `abc`，需要计算一个 `[前驱, 后继)` 区间：

- 后继：给前缀末尾拼上 `{`（`z` 之后的 ASCII 字符）。
- 前驱：把前缀最后一个字符替换成字母表中的前一个字符（字母表定义为 `` `abc...z{ ``，反引号在 `a` 之前）。

因为不知道这两个边界值是否真实存在于 ZSET 里，技巧是：插入两个带 UUID 后缀的哨兵成员，用 `ZRANK` 查它们的位置，再按位置区间 `ZRANGE` 取数据，最后删除哨兵。整个过程用 `WATCH`/`MULTI`/`EXEC` 包起来，防止两个用户同时搜索时互相踩到对方的哨兵。

**国际化提醒**（原书侧栏）：非 ASCII 字母表要选一个字节安全的编码（UTF-8，或大端序的 UTF-16/32——小端序不适用这个技巧），前驱/后继字符换成该编码下的最小值（null 字节）和最大值。

作者后来在 6.2.5 节自己吐槽：这套哨兵+WATCH方案"比实际需要的复杂"，用一把锁就能大幅简化——这是本章反复出现的主题：**先用 WATCH 实现正确性，再用锁简化代码，最后（第 11 章）用 Lua 做到又快又简单**。

## 6.2 分布式锁

### 为什么需要锁：WATCH 在高并发下会退化

原书用一个真实的负载测试说明问题（5 个卖家 + 5 个买家，60 秒）：不加锁时，重试次数能飙到 **16 万次**，平均等待 **498ms**；加一把粗粒度锁后，重试几乎归零，延迟降到 **14ms**；把锁细化到单个商品级别（`market:<item>`），吞吐进一步提升到 **22 万次/秒**左右，延迟 &lt;3ms。这组数据直观地说明了**乐观锁（WATCH）在低竞争下很好，但高竞争下会引发重试风暴**。

### 锁的四种"看起来正确但其实错误"的实现

原书专门列出常见错误模式（这依然是今天面试/代码审查里检查分布式锁实现的标准清单）：

1. 持有者操作耗时过长，锁自动过期，但持有者不知道自己已经"失去"了锁，可能释放了别人的锁。
2. 持有者长时间操作后崩溃，其他等待者无法感知，只能傻等超时。
3. 锁超时后，多个客户端同时抢到锁。
4. 以上组合：多个进程都以为自己是唯一持锁者。

原书还提到一个很扎实的验证方法：作者亲测了几个当时市面上的 Redis 锁实现，5 个客户端跑 10 秒，**至少一半的实现出现了锁重复持有**的问题。

### 正确的锁实现

```python
def acquire_lock(conn, lockname, acquire_timeout=10):
    identifier = str(uuid.uuid4())  # 每个持锁者独一无二的身份标识，防止误删别人的锁
    end = time.time() + acquire_timeout
    while time.time() < end:
        if conn.setnx('lock:' + lockname, identifier):
            return identifier
        time.sleep(0.001)
    return False

def release_lock(conn, lockname, identifier):
    pipe = conn.pipeline(True)
    while True:
        try:
            pipe.watch('lock:' + lockname)
            if pipe.get('lock:' + lockname) == identifier:
                pipe.multi()
                pipe.delete('lock:' + lockname)
                pipe.execute()
                return True
            pipe.unwatch()
            break
        except redis.exceptions.WatchError:
            pass
    return False
```

关键设计点：用 UUID 作为"锁身份令牌"，释放前必须验证令牌匹配——**防止 A 的锁超时后被 B 拿到，A 却误删了 B 的锁**。

**现代提醒（原书自己在 6.2.5 也点出了）**：Redis 2.6.12 之后，`SET key value NX EX seconds` 一条命令就能做到"不存在才设置 + 带过期时间"，原书需要 `SETNX` + 单独 `EXPIRE` 两步（中间还有崩溃窗口，需要额外逻辑兜底）的写法已经可以简化成一行。**但释放逻辑（验证令牌 + 删除）依然需要 WATCH 或 Lua，这一点没有变**。

**现代生产实践**：如果你要在生产环境用 Redis 做分布式锁，建议直接使用成熟的库而不是照抄这段代码：

- Python：`redis-py` 自带 `Redis.lock()`，或 `python-redis-lock`。
- Java：Redisson 的 `RLock`（支持看门狗自动续期）。
- Node/TS：`redlock` npm 包。
- 如果需要跨多个独立 Redis 实例的强一致性锁，可以了解 **RedLock 算法**（原书完全没有提到，因为它是后来才提出的，且业界对其正确性有争议——Martin Kleppmann 曾撰文质疑 RedLock 在时钟漂移下的安全性，antirez 也做了回应；如果你的锁需要"绝对不能被两个进程同时持有"这种强保证，更稳妥的选择是用 Zookeeper/etcd 这类基于共识协议的系统，而不是 Redis）。

**Java（Jedis + Redisson 风格自实现）**

```java
public String acquireLock(UnifiedJedis jedis, String lockName, long timeoutSec) {
    String identifier = UUID.randomUUID().toString();
    String key = "lock:" + lockName;
    long end = System.currentTimeMillis() + timeoutSec * 1000;
    while (System.currentTimeMillis() < end) {
        if ("OK".equals(jedis.set(key, identifier, new SetParams().nx().ex(10)))) {
            return identifier;
        }
        try { Thread.sleep(1); } catch (InterruptedException ignored) {}
    }
    return null;
}

public boolean releaseLock(UnifiedJedis jedis, String lockName, String identifier) {
    String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                     "return redis.call('del', KEYS[1]) else return 0 end";
    Object result = jedis.eval(script, List.of("lock:" + lockName), List.of(identifier));
    return Long.valueOf(1).equals(result);
}
```

**TypeScript（ioredis，释放用 Lua 保证原子性）**

```ts
import { Redis } from "ioredis";
import { randomUUID } from "crypto";

const redis = new Redis();

export async function acquireLock(lockName: string, timeoutSec = 10): Promise<string | null> {
  const identifier = randomUUID();
  const end = Date.now() + timeoutSec * 1000;
  while (Date.now() < end) {
    const ok = await redis.set(`lock:${lockName}`, identifier, "EX", 10, "NX");
    if (ok === "OK") return identifier;
    await new Promise((r) => setTimeout(r, 1));
  }
  return null;
}

const releaseScript = `
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end`;

export async function releaseLock(lockName: string, identifier: string): Promise<boolean> {
  const result = await redis.eval(releaseScript, 1, `lock:${lockName}`, identifier);
  return result === 1;
}
```

> 注意释放锁这里我们直接用 Lua 脚本代替原书的 WATCH/MULTI/EXEC——这正是第 11 章要讲的演进方向，提前用上更简洁。

## 6.3 计数信号量

信号量是"允许 N 个并发持有者的锁"（mutex 就是 N=1 的信号量）。原书场景：给每个账号的市场 API 限制最多 5 个并发进程访问。

- **基础版（按时钟排序）**：ZSET 存 `{标识: 时间戳}`，先 `ZREMRANGEBYSCORE` 清理超时的旧持有者，`ZADD` 自己，`ZRANK` 检查排名是否 &lt; 限额。**明确的公平性隐患**：依赖所有客户端时钟一致，如果 A 的时钟比 B 慢 10ms，B 可能在 A 不知情的情况下"偷走"了 A 的名额。
- **公平版（按计数器排序）**：额外维护一个原子自增计数器和一个 "owner" ZSET，用计数器值（而不是时间戳）决定顺序，避免依赖系统时钟。**32 位平台警告**：计数器是有符号 32 位整数，高频信号量可能在 ~2 小时内溢出——建议用 64 位平台。
- **仍然有残余竞态**：公平版本里，A 先 INCR 拿到计数器值，但 B 的 ZADD+ZRANK 检查先完成，B 可能拿到本该属于 A 的名额。最终解法是**用第 6.2 节的锁把整个"公平信号量获取"过程包起来**——这再次印证了本章的核心方法论：**锁是构建更复杂并发原语的基础组件**。

作者明确给出三级权衡建议：信任时钟且能接受偶尔超限 → 用基础版；时钟只在 1~2 秒内可信 → 用公平版；必须绝对精确 → 锁包装的公平版（作者原话："一般来说，坚持用最严格的最后一种版本是个好主意"）。

**现代替代**：如果只是想限流/限并发，今天有更简单的选择——**令牌桶/漏桶算法配合 Redis Lua 脚本**（社区有大量现成实现，如 `redis-cell` 模块提供 `CL.THROTTLE` 命令直接做限流），或者用 API 网关层的限流功能（如 Kong、Envoy、云厂商 API Gateway），不一定需要在应用代码里手写 ZSET 信号量。

## 6.4 任务队列

### 简单 FIFO 队列

`RPUSH` 入队，`BLPOP` 阻塞出队——最基础的队列模式。原书进一步展示了：

- **多任务类型的通用 worker**：任务编码成 `[函数名, 参数列表]`，worker 用一个回调字典按函数名分发。
- **优先级队列**：`BLPOP` 支持传入多个队列名的列表，会按顺序检查，第一个非空的队列获胜——传 `[high, medium, low]` 就实现了严格优先级。

### 延迟任务

用一个额外的 ZSET `delayed:`（分数是应该执行的时间戳）存暂缓任务，一个独立的轮询进程 `poll_queue()` 不断检查最早到期的任务，到期就搬到真正的队列里，用**按任务 ID 的细粒度锁**防止多个轮询进程重复搬运。

原书明确指出 ZSET 没有类似 `BLPOP` 的阻塞弹出原语，所以只能轮询（`sleep(0.01)`），并建议可以做自适应退避（没有任务时增大 sleep 间隔）来减少空转开销。

**现代替代——这正是 Redis Streams 最擅长的场景**：

- Stream 的 `XADD`/`XREADGROUP`/`XACK` 组合天然支持"多 worker 消费同一个流、每条消息独立 ACK、未 ACK 的消息可以被其他 worker 认领（`XCLAIM`/`XAUTOCLAIM`）"，比原书这套"LIST + 锁 + 手写 worker 分发"的方案更完备。
- 延迟任务在 Stream 生态里通常配合独立的"延迟队列"实现（比如 Redis 官方没有原生延迟 Stream，但可以用 ZSET 存到期时间 + 一个搬运进程，思路和原书完全一致——**Streams 解决的是"可靠消费"，不是"延迟调度"，这两个问题原书的方案至今仍是合理参照**）。
- 更重量级的场景（跨语言、需要重试策略、死信队列、可观测性），直接上专业消息队列（RabbitMQ、Kafka、AWS SQS）通常比在 Redis 里手搭更省心，这也是原书作者自己的态度——他提到了自己开源的 `rpqueue` 项目，也承认 Ruby 生态的 Resque 库做得比书里 11 行代码的例子更完整。

## 6.5 拉模式消息（Pull Messaging）

### 单收件人

`mailbox:<user>` 是一个 LIST，发送方 `RPUSH`，接收方按自己的节奏 `LPOP`/`LRANGE`+`LTRIM`。相比 pub/sub，即使接收方长时间离线，消息也不会丢失。

### 多收件人（群聊）

数据模型（四个结构配合）：

- `chat:<chat_id>`：ZSET，member=用户名，score=该用户在这个聊天里已读到的最大消息 ID。
- `seen:<user>`：ZSET，member=chat_id，score=已读到的最大消息 ID。
- `msgs:<chat_id>`：ZSET，member=JSON 消息，score=消息 ID。
- 一个自增计数器给每个聊天生成递增消息 ID。

发送消息需要读取当前最大消息 ID 再写入新消息，这是一个"读后写"场景，原书解释了为什么这里选择用**锁**而不是 WATCH：如果用 WATCH，每个**接收者**读取/清理消息时都要处理潜在的重试，而把复杂度放在发送端（用锁保护发送）能让所有接收者的读取路径更简单——**这是一个"把复杂度放在写多读少的一端 还是写少读多的一端"的架构权衡**，原书在这里选择让"发送"（相对少）承担锁开销，让"接收"（相对多）保持简单无锁。

清理逻辑很巧妙：`fetch_pending_messages()` 每次都会检查这条聊天里"所有参与者都已读到的最小消息 ID"，把这之前的消息从 `msgs:` 里删掉——**已读回执驱动的垃圾回收**。

**现代替代**：这正是 Redis Streams 的教科书级应用场景。一个 Stream 天然支持"每个消费者独立的读取位置"（`XREADGROUP` 的消费组游标），不需要像原书这样手工维护 `seen:`/`chat:` 两个 ZSET 来模拟"谁读到哪了"。如果今天要做聊天系统的消息存储，用一个 Stream + 消费组几乎可以替代整个 6.5.2 节的设计，代码量会小很多。不过，原书这里展示的"用已读位点驱动数据清理"这个思路，在 Stream 里对应的是 `XTRIM`/`MINID` 策略——理解了原书的设计动机，会更容易理解为什么 Stream 要这样设计裁剪机制。

## 6.6 用 Redis 分发文件

用 Redis 在多台机器间传输日志文件（而不是 NFS/Rsync/BitTorrent），核心动机是**允许消费者在文件完全到达之前就开始处理**。发送方把文件按 128KB 分块 `APPEND` 进一个 STRING key，用第 6.5.2 节的群聊机制通知消费者"文件名已就绪"；消费者用 `SUBSTR`/`GETRANGE` 分块读取（`readblocks()`），支持透明 gzip 解压（手工解析 gzip header + `zlib.decompressobj` 做流式解压）。

**现代替代**：今天做跨机器/跨服务的文件分发，几乎不会再选择"把文件塞进 Redis STRING"这条路——**对象存储（S3/OSS/MinIO）+ 事件通知（S3 Event → SQS/Lambda）**、或者直接上 Kafka（本来就支持大体量、分区、多消费者），都比这个方案更适合真实的日志管道场景。这一节在今天更大的价值是**教你怎么用 Redis 的基础命令（APPEND/GETRANGE + pub/sub 通知）拼出一个流式传输协议**——这个"拼积木"的思维方式本身是可迁移的能力，即使具体的实现今天不会照抄。

## 本章小结

原书总结了两条核心经验：(1) 一把正确实现的分布式锁，往往比纯 WATCH 更容易写对、性能更好；(2) 组件是可以复用的——锁被复用进了信号量、延迟队列、多收件人消息；多收件人消息机制又被复用进了文件分发。

**给现代读者的更新地图**：

| 原书方案 | 现代优先选择 |
|---|---|
| WATCH/MULTI/EXEC 手工加锁 | `SET NX EX` + Lua 释放；生产用 Redisson/redlock 库 |
| ZSET 手写计数信号量 | 令牌桶算法（如 `redis-cell` 模块）或网关限流 |
| LIST + BLPOP 任务队列/延迟任务 | Redis Streams（消费组、ACK、死信）；重量级场景用专业 MQ |
| LIST 拉模式消息 / ZSET 群聊消息 | Redis Streams（每消费者独立游标） |
| STRING APPEND 分块传文件 | 对象存储 + 事件通知，或 Kafka |
