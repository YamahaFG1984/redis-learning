第 1 章

第 1 章 认识 Redis

对应原书第 1 章 "Getting to know Redis"。

1.0 作者的开场故事

作者提到自己曾把一个跑在 SQL 上的客户联系人搜索系统（6 万行数据，查询要 10~15 秒）用一周时间搬到 Redis 上，响应时间降到 50ms 以内，后续优化后整体提升了约 200 倍。这不是虚构的营销话术，而是 Redis 诞生的真实场景——当你的问题是"频繁地对内存量级的数据做简单读写"时，关系型数据库的通用性反而是负担。

1.1 Redis 是什么

Redis 官方定义在这些年基本没变，但内涵扩充了很多：

  • 2013 年原书的定义：一个非关系型、键值到 5 种数据结构的映射数据库，内存存储 + 可落盘持久化，支持复制做读扩展，客户端分片做写扩展。
  • 现代定义（Redis 7.x/8.x）：Redis 从"5 种数据结构"扩展到了 STRING、LIST、SET、HASH、ZSET、Stream（消息流，5.0+）、HyperLogLog、Bitmap/Bitfield、Geo（地理位置），以及通过 Redis Stack/Redis 8 内置的 JSON、时序（TimeSeries）、概率数据结构（Bloom/Cuckoo Filter）、全文搜索/向量检索（Search）。2024 年 Redis 改变了开源协议（转向 RSALv2/SSPLv1 双协议），社区分叉出了 Valkey（Linux Foundation 托管，多数云厂商现在默认提供 Valkey）；2025 年 Redis 又宣布回归 AGPLv3 开源。这段协议历史值得了解，但不影响本书讲的核心数据结构和命令语义——Valkey 与 Redis 在协议层几乎完全兼容。

原书对比 Redis 和 memcached/MySQL/PostgreSQL/MongoDB 的表格，放到今天可以这样更新：

Redis（现代）MemcachedPostgreSQLMongoDB
类型内存优先，多结构 KV内存 KV关系型文档型
结构String/List/Set/Hash/ZSet/Stream/JSON/Bitmap/Geo/概率结构只有字符串表文档（JSON-like）
持久化RDB + AOF（可混合）、副本、Redis Cluster无WALJournal + 副本集
扩展能力Lua 脚本、Redis Functions、模块（Search/JSON/TimeSeries）无存储过程、扩展聚合管道

为什么不用 memcached？ memcached 只有字符串，想实现"列表"得自己拼字符串再解析；Redis 原生提供 5+ 种结构，代码更短、更快、更不容易出错。为什么不用关系型数据库？ 关系型数据库擅长"插入新行"（顺序写盘），不擅长"频繁更新同一行的聚合值"（随机 IO）；Redis 直接在内存里原子自增，没有 SQL 解析/优化器开销。

1.2 五（现在是十几）种数据结构长什么样

原书的 Table 1.2（STRING/LIST/SET/HASH/ZSET）依然是 Redis 的核心心智模型，值得先吃透再往下学：

结构存的是什么典型命令
STRING字符串/整数/浮点数GET/SET/INCR/APPEND
LIST允许重复元素的有序链表LPUSH/RPUSH/LRANGE/LPOP
SET无序不重复字符串集合SADD/SMEMBERS/SINTER
HASH字段→值的映射HSET/HGET/HGETALL
ZSET带分数、按分数排序的唯一成员集合ZADD/ZRANGE/ZRANGEBYSCORE

现代补充的结构（原书完全没有，但今天写 Redis 应用几乎绕不开）：

  • Bitmap（SETBIT/GETBIT/BITCOUNT/BITOP，本质是 STRING）：签到、布尔标记位图。
  • HyperLogLog（PFADD/PFCOUNT/PFMERGE）：用 12KB 固定内存估算海量数据的基数（去重计数），误差率 <1%。
  • Geo（GEOADD/GEOSEARCH，本质是 ZSET + geohash 编码）：附近的人/门店。
  • Stream（XADD/XREAD/XREADGROUP，Redis 5.0+）：真正的消息队列，带消费组、ACK、持久化游标——这几乎完全取代了原书第 6 章手写队列/pub-sub 消息投递的必要性。
  • JSON（JSON.SET/JSON.GET，Redis Stack/Redis 8 内置）：直接在 Redis 里存嵌套 JSON 并按路径读写，一定程度回应了原书 2.4 节"Redis 不支持嵌套结构"这个长期痛点。
  • HASH 字段级 TTL（HEXPIRE/HPERSIST，Redis 7.4+）：给 HASH 里的单个字段设置过期时间。

1.3 Hello Redis：一个投票系统

原书用一个 Reddit/Hacker News 风格的文章投票系统贯穿全章，这是学 Redis 最经典的入门案例，建议动手实现一遍。

数据建模

  • article:<id>：HASH，存 title/link/poster/time/votes。
  • score:：ZSET，member 是 article:<id>，score 是"发布时间 + 每票 432 分"算出来的热度分。
  • time:：ZSET，member 同上，score 是发布时间，用于"按最新排序"。
  • voted:<id>：SET，记录谁投过票，防止重复投票，一周后过期。

432 这个数字怎么来的：作者希望 200 票能让文章获得大约"一天"的热度加成，86400 秒 ÷ 200 票 = 432 分/票。这是一个很好的例子——分数不是拍脑袋定的，是从业务目标反推出来的。

投票逻辑（原书 Listing 1.6）

def article_vote(conn, user, article):
    cutoff = time.time() - ONE_WEEK_IN_SECONDS
    if conn.zscore('time:', article) < cutoff:
        return
    article_id = article.partition(':')[-1]
    if conn.sadd('voted:' + article_id, user):
        conn.zincrby('score:', article, VOTE_SCORE)
        conn.hincrby(article, 'votes', 1)

原书自己承认这里有个正确性问题：SADD（记录投票人）和后面的 ZINCRBY/HINCRBY（加分）不是原子的一整体——理论上可能在两步之间崩溃，导致"记录了投票人但分数没加"。这个问题第 3、4 章才会用 WATCH/MULTI/EXEC 解决。

现代做法：今天写这段逻辑，直接建议用 Lua 脚本或 Redis Function 把"检查时间窗 + SADD + ZINCRBY + HINCRBY"打包成一个原子操作（第 11 章会系统讲 Lua）。这是原书埋下的伏笔，也是贯穿全书的一条主线——从"多步操作的竞态"到"Lua 原子脚本"的演进。

现代 Redis 客户端代码（三语言）

Python（redis-py）

import time
import redis

r = redis.Redis(decode_responses=True)

ONE_WEEK = 7 * 86400
VOTE_SCORE = 432

def article_vote(user: str, article: str):
    cutoff = time.time() - ONE_WEEK
    if r.zscore("time:", article) is None or r.zscore("time:", article) < cutoff:
        return
    article_id = article.partition(":")[-1]
    if r.sadd(f"voted:{article_id}", user):
        r.zincrby("score:", VOTE_SCORE, article)  # 注意：现代 zincrby 是 (name, amount, value)
        r.hincrby(article, "votes", 1)

def post_article(user: str, title: str, link: str) -> str:
    article_id = str(r.incr("article:"))
    voted_key = f"voted:{article_id}"
    r.sadd(voted_key, user)
    r.expire(voted_key, ONE_WEEK)

    now = time.time()
    article = f"article:{article_id}"
    r.hset(article, mapping={
        "title": title, "link": link, "poster": user,
        "time": now, "votes": 1,
    })
    r.zadd("score:", {article: now + VOTE_SCORE})
    r.zadd("time:", {article: now})
    return article_id

对比原书：原书 conn.hmset(article, {...}) 用的是 HMSET——Redis 4.0 起 HSET 本身就支持一次写多个字段，HMSET 已被标记为 deprecated，新代码应该直接用 HSET。conn.zadd('score:', article, now + VOTE_SCORE) 是老版 redis-py 的位置参数写法，现代 redis-py 要求 zadd(name, {member: score}) 字典形式。

Java（Jedis）

import redis.clients.jedis.UnifiedJedis;
import java.util.HashMap;
import java.util.Map;

public class ArticleVoting {
    static final long ONE_WEEK = 7 * 86400L;
    static final double VOTE_SCORE = 432;

    public static void articleVote(UnifiedJedis jedis, String user, String article) {
        Double postTime = jedis.zscore("time:", article);
        if (postTime == null || postTime < System.currentTimeMillis() / 1000.0 - ONE_WEEK) return;
        String articleId = article.split(":")[1];
        if (jedis.sadd("voted:" + articleId, user) == 1) {
            jedis.zincrby("score:", VOTE_SCORE, article);
            jedis.hincrBy(article, "votes", 1);
        }
    }

    public static String postArticle(UnifiedJedis jedis, String user, String title, String link) {
        String articleId = String.valueOf(jedis.incr("article:"));
        String votedKey = "voted:" + articleId;
        jedis.sadd(votedKey, user);
        jedis.expire(votedKey, ONE_WEEK);

        double now = System.currentTimeMillis() / 1000.0;
        String article = "article:" + articleId;
        Map<String, String> fields = new HashMap<>();
        fields.put("title", title);
        fields.put("link", link);
        fields.put("poster", user);
        fields.put("time", String.valueOf(now));
        fields.put("votes", "1");
        jedis.hset(article, fields);
        jedis.zadd("score:", now + VOTE_SCORE, article);
        jedis.zadd("time:", now, article);
        return articleId;
    }
}

TypeScript（ioredis）

import { Redis } from "ioredis";
const redis = new Redis();

const ONE_WEEK = 7 * 86400;
const VOTE_SCORE = 432;

export async function articleVote(user: string, article: string) {
  const postTime = await redis.zscore("time:", article);
  if (postTime === null || Number(postTime) < Date.now() / 1000 - ONE_WEEK) return;

  const articleId = article.split(":")[1];
  const added = await redis.sadd(`voted:${articleId}`, user);
  if (added) {
    await redis.zincrby("score:", VOTE_SCORE, article);
    await redis.hincrby(article, "votes", 1);
  }
}

export async function postArticle(user: string, title: string, link: string) {
  const articleId = String(await redis.incr("article:"));
  const votedKey = `voted:${articleId}`;
  await redis.sadd(votedKey, user);
  await redis.expire(votedKey, ONE_WEEK);

  const now = Date.now() / 1000;
  const article = `article:${articleId}`;
  await redis.hset(article, { title, link, poster: user, time: now, votes: 1 });
  await redis.zadd("score:", now + VOTE_SCORE, article);
  await redis.zadd("time:", now, article);
  return articleId;
}

分页取文章（原书 Listing 1.8）

原书用 ZREVRANGE（按排名取一段，不是按分数）取一页文章 ID，再挨个 HGETALL。这里有个原书文字和代码不一致的小细节：正文说的是 ZREVRANGEBYSCORE，但代码实际用的是 ZREVRANGE——如果你对照原书排查问题，记得代码才是准的。

现代写法应该用 pipeline 把"批量 HGETALL"合并成一次网络往返（原书自己在第 3 章把这个当成一道练习题留给读者）：

def get_articles(page: int = 1, order: str = "score:", per_page: int = 25):
    start = (page - 1) * per_page
    ids = r.zrevrange(order, start, start + per_page - 1)
    pipe = r.pipeline()
    for aid in ids:
        pipe.hgetall(aid)
    rows = pipe.execute()
    return [dict(row, id=aid) for aid, row in zip(ids, rows) if row]

文章分组（原书 Listing 1.9/1.10）

用 SADD/SREM 把文章加入/移出 group:<name> 这个 SET，查询某个分组下按热度排序的文章时，用 ZINTERSTORE（aggregate='max'）把 group:<name> 和 score: 相交，结果缓存 60 秒（EXPIRE）。

作者在这里点出一个很朴素但常被忽视的设计原则：如果一篇文章只属于一两个分组，直接把分组存进文章的 HASH、每次投票顺手 ZINCRBY 那一两个分组的分数就够了；但如果文章可能属于任意多个分组，每次投票都全量更新所有分组的分数代价太高，所以改成"定期重新计算"而不是"实时增量更新"——这是一个通用的权衡：实时精确 vs 定期批量重算，贯穿几乎所有排行榜/统计类系统的设计。

1.5 本章小结

本章小结

Redis 是工具，不是银弹。它的核心差异化在于：内存（快）、远程（可被多进程/多机共享）、持久化（能扛重启）、可扩展（复制/分片）。原书希望读者从"如何把数据塞进表和行"转变为"哪种 Redis 结构最适合这个问题"——这个心智模型转变到今天依然是学 Redis 的第一课，比任何具体命令都重要。
