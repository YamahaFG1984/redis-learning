# 第 16 章（补充）数据分层与结构选型方法论

> 本章不对应原书任何一章,而是这本笔记在教学过程中被反复问到的一个问题:"以前 Redis 用得少,写业务的时候该把哪些数据放数据库、哪些放 Redis、放 Redis 又该选哪种类型,缺一套自己的判断方法论"。原书通篇都在用具体案例(投票系统、购物车、时间线)演示"该用哪个结构",但没有把背后的判断逻辑单独总结成方法论——本章把它显式化。

## 16.1 第一层判断:这份数据该进数据库还是 Redis

把 Redis 默认当成"可能丢"的存储来设计——即使开了 RDB/AOF 持久化,主从切换、机器故障时仍有丢数据的窗口。围绕这个前提,依次问自己四个问题:

1. **丢了这份数据,后果有多严重?** 会有财务/法律/客诉后果(订单、支付、账户余额、合同、交易流水)→ 必须落 DB,Redis 最多做加速层。丢了顶多体验差一点、能重算或重新拉取(缓存、排行榜、推荐结果、会话)→ 可以放 Redis。
2. **这份数据是"真相源"还是"衍生数据"?** System of Record(用户资料、订单、审计日志)→ DB 存,Redis 顶多缓存一份。Derived data(热度榜、聚合统计、搜索索引)→ 天然适合 Redis,丢了可以从源头重建。Ephemeral(会话、验证码、限流计数、分布式锁)→ 不该进 DB,这类数据生来就有 TTL,Redis 的 `EXPIRE` 是原生能力,DB 反而要自己写清理逻辑。
3. **需要的是"速度"还是 Redis 的"原子能力"?** 有些场景不是"数据库查询慢所以缓存一下",而是问题本身就该用 Redis 结构建模:高并发原子自增/自减(库存扣减、点赞数)、自动维持排序(排行榜)、集合运算(共同好友、标签匹配)、极低成本去重计数(UV)、分布式锁/限流原语。这类场景第一反应就该是 Redis,不管数据量大不大。
4. **访问模式是不是"读多写少 + 延迟敏感"?** 如果是,且数据集符合二八定律(20% 热数据占 80% 访问量)→ 经典缓存模式:全量在 DB,热数据子集缓存到 Redis。如果需要复杂多条件查询/JOIN/全文检索,Redis 不擅长,该用 DB 或专门的搜索引擎(见第 7、15 章)。

## 16.2 第二层判断:进了 Redis 该选哪个结构

拿到一份要放 Redis 的数据,按顺序问自己:

**一个新手最容易纠结的点——STRING 存 JSON,还是用 HASH?**

- 总是整存整取,不需要单独改某个字段 → STRING 存 JSON,序列化简单。
- 经常只改一两个字段(购物车只改某个商品数量)→ HASH,避免整体反序列化再序列化。
- HASH 还有个内存优势:小 HASH 会用紧凑的 listpack 编码存储,比一堆零散的 STRING key 更省内存(细节见第 9 章)。

## 16.3 常见业务场景速查表

| 场景 | 结构 | 为什么 |
|---|---|---|
| 用户登录会话 | HASH | 字段化,可单独续期/改字段 |
| 排行榜/热度榜 | ZSET | 自带排序 |
| 分布式锁 | STRING（`SET NX EX`） | 原子性 + 自动过期 |
| 限流计数器 | STRING（`INCR`）或 ZSET（滑动窗口） | 原子自增 |
| 关注关系 | SET 或 ZSET | 集合运算/按时间排序 |
| Feed 时间线 | ZSET | 按时间排序 |
| 购物车 | HASH | 按商品字段增减 |
| 消息队列（需 ack/多消费者） | Stream | 原生支持消费组 |
| 签到/打卡 | Bitmap | 海量布尔状态省内存 |
| 网站 UV 去重计数 | HyperLogLog | 12KB 存近似基数 |
| 库存扣减 | STRING（`DECR`） | 原子操作防止超卖 |
| 验证码/一次性 token | STRING + `EXPIRE` | 天然临时数据 |

### 16.4.3 分布式锁（STRING，SET NX EX + Lua 校验归属再释放）

```python
import uuid

UNLOCK_SCRIPT = """
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
"""

def acquire_lock(lock_key: str, ttl: int = 10) -> str | None:
    token = str(uuid.uuid4())
    ok = r.set(lock_key, token, nx=True, ex=ttl)
    return token if ok else None

def release_lock(lock_key: str, token: str) -> bool:
    return bool(r.eval(UNLOCK_SCRIPT, 1, lock_key, token))
```

```java
import redis.clients.jedis.params.SetParams;
import java.util.Collections;
import java.util.UUID;

static final String UNLOCK_SCRIPT =
    "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";

public static String acquireLock(String lockKey, int ttlSeconds) {
    String token = UUID.randomUUID().toString();
    String ok = jedis.set(lockKey, token, SetParams.setParams().nx().ex(ttlSeconds));
    return "OK".equals(ok) ? token : null;
}

public static boolean releaseLock(String lockKey, String token) {
    Object result = jedis.eval(UNLOCK_SCRIPT, Collections.singletonList(lockKey), Collections.singletonList(token));
    return Long.valueOf(1).equals(result);
}
```

### 16.4.8 消息队列（Stream，带消费组 + ack）

```python
def produce(stream: str, payload: dict):
    r.xadd(stream, payload)

def consume(stream: str, group: str, consumer: str, count: int = 10):
    try:
        r.xgroup_create(stream, group, id="0", mkstream=True)
    except redis.ResponseError:
        pass  # 消费组已存在
    entries = r.xreadgroup(group, consumer, {stream: ">"}, count=count)
    for _, messages in entries or []:
        for msg_id, fields in messages:
            process(fields)
            r.xack(stream, group, msg_id)
```

```java
import redis.clients.jedis.StreamEntryID;
import redis.clients.jedis.params.XReadGroupParams;
import redis.clients.jedis.resps.StreamEntry;
import java.util.Map;

public static void produce(String stream, Map<String, String> payload) {
    jedis.xadd(stream, StreamEntryID.NEW_ENTRY, payload);
}

public static void consume(String stream, String group, String consumer) {
    var entries = jedis.xreadGroup(group, consumer,
        XReadGroupParams.xReadGroupParams().count(10),
        Map.of(stream, StreamEntryID.UNRECEIVED_ENTRY));
    if (entries == null) return;
    for (var entry : entries) {
        for (StreamEntry e : entry.getValue()) {
            process(e.getFields());
            jedis.xack(stream, group, e.getID());
        }
    }
}
```

```ts
export async function produce(stream: string, payload: Record<string, string>) {
  const fields = Object.entries(payload).flat();
  await redis.xadd(stream, "*", ...fields);
}

export async function consume(stream: string, group: string, consumer: string) {
  try {
    await redis.xgroup("CREATE", stream, group, "0", "MKSTREAM");
  } catch {
    // 消费组已存在
  }
  const res = await redis.xreadgroup("GROUP", group, consumer, "COUNT", 10, "STREAMS", stream, ">");
  if (!res) return;
  for (const [, messages] of res as any) {
    for (const [id, fields] of messages) {
      process(fields);
      await redis.xack(stream, group, id);
    }
  }
}
```

### 16.4.12 验证码/一次性 token（STRING + EXPIRE，验证后立即删除防重放）

```python
import random

def send_code(phone: str) -> str:
    code = f"{random.randint(0, 999999):06d}"

def verify_code(phone: str, code: str) -> bool:

    saved = r.get(key)
    if saved == code:
        r.delete(key)
        return True
    return False
```

```java
import java.util.concurrent.ThreadLocalRandom;

public static String sendCode(String phone) {

public static boolean verifyCode(String phone, String code) {
    String key = "otp:" + phone;

    return false;
}
```

export async function sendCode(phone: string): Promise<string> {
  const code = String(Math.floor(Math.random() * 1_000_000)).padStart(6, "0");
  await redis.set(`otp:${phone}`, code, "EX", 300);
  return code;
}

export async function verifyCode(phone: string, code: string): Promise<boolean> {
  const key = `otp:${phone}`;
  const saved = await redis.get(key);
  if (saved === code) {
    await redis.del(key);
    return true;
  }
  return false;
}

## 16.5 常见反模式

- **把 Redis 当成唯一存储去存不能丢的数据**——没有 DB 兜底的"真相源",出故障就是真丢。
- **不管什么数据都用 STRING 存整个 JSON**——该用 HASH/ZSET 建模的结构化数据硬塞进字符串,应用层要反复整体序列化/反序列化,也丧失了 Redis 原生的原子操作能力。
- **单个 key 存超大 value**(几十 MB 的大列表/大 JSON)——读写会阻塞,也容易造成内存碎片,详见第 9 章。
- **缓存了但没设计失效策略**——导致缓存和数据库不一致,或引发缓存穿透/击穿/雪崩,详见第 2 章页面缓存部分。

## 本章小结

这套方法论的核心是两层过滤:第一层判断"这份数据能不能丢、是不是真相源",决定它该不该进 Redis;第二层判断"这是一个值还是一组值、要不要排序、要不要原子运算",决定选哪个结构。原书用一个个具体案例(投票系统、购物车、时间线)教会你怎么做,这一章把背后反复出现的判断逻辑显式地总结出来——以后遇到新的业务需求,可以直接对照本章的两张决策图和速查表,而不必凭直觉猜。
