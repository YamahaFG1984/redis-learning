# 第 15 章（补充）Redis 与 AI 应用：向量检索与语义缓存

> 本章是原书没有覆盖的内容，也是这几年 Redis 应用场景里增长最快的一块。2013 年还没有"向量数据库"这个概念，但 Redis 这些年通过 RediSearch 模块把向量相似度检索原生集成了进来（现已并入 Redis 8 / Redis Stack），使得 Redis 可以直接承担 RAG（检索增强生成）系统里的向量存储角色，不需要额外引入 Pinecone/Milvus/Weaviate 这类专用向量数据库。

## 15.0 为什么 Redis 能做向量检索

本质上，向量检索要解决的问题和原书第 7 章的搜索/排序是**同一类问题**——"给定一个查询，找出最相关的一批结果，按相关度排序"。区别只在于"相关度"的计算方式：原书第 7 章靠倒排索引 + 词匹配打分，向量检索靠**embedding 之间的余弦相似度/欧氏距离**。理解了原书第 7 章"倒排索引 + ZSET 打分"的思路，再学向量检索会顺畅很多——它们是同一个"排序检索"问题的不同数据表示。

## 15.1 核心概念

- **Embedding（向量嵌入）**：把文本/图片/音频通过模型转换成一个固定长度的浮点数数组（比如 1536 维），语义相近的内容在向量空间里距离也相近。
- **向量索引算法**：`FLAT`（暴力全量比对，精确但慢，适合小数据集）、`HNSW`（分层导航小世界图，近似最近邻，速度快，是生产环境的主流选择）。
- **距离度量**：`COSINE`（余弦相似度，文本 embedding 最常用）、`L2`（欧氏距离）、`IP`（内积）。

## 15.2 用 RediSearch 建向量索引

```bash
FT.CREATE idx:articles ON HASH PREFIX 1 article: SCHEMA \
    title TEXT \
    content TEXT \
    embedding VECTOR HNSW 6 \
        TYPE FLOAT32 \
        DIM 1536 \
        DISTANCE_METRIC COSINE
```

这条命令直接建立了一个**混合索引**——`title`/`content` 是传统全文字段（对应原书第 7 章的倒排索引玩法），`embedding` 是向量字段。这意味着**你可以在一次查询里同时做"关键词过滤 + 语义相似度排序"**，这是原书第 7 章手写方案完全做不到的能力（原书的 ZSET 组合排序技巧只能组合数值分数，没法表达"语义相似"这种概念）。

### KNN 查询

```bash
FT.SEARCH idx:articles "*=>[KNN 5 @embedding $vec AS score]" \
    PARAMS 2 vec "\x01\x02\x03..." \
    SORTBY score ASC DIALECT 2
```

### 混合查询：关键词过滤 + 向量排序

```bash
FT.SEARCH idx:articles "(@title:redis)=>[KNN 10 @embedding $vec AS score]" \
    PARAMS 2 vec "..." SORTBY score DIALECT 2
```

先用 `@title:redis` 做关键词过滤缩小候选集，再对候选集做向量排序——这正是原书第 7 章"先用 SET 交集缩小范围，再用 ZSET 排序"这个模式的现代演进版，只是排序依据从"投票数/时间"换成了"语义相似度"。

## 15.3 RAG（检索增强生成）系统里 Redis 的角色

一个典型 RAG 流程：

```
用户提问 → 生成 query embedding → Redis 向量检索找 Top-K 相关文档
        → 把文档内容拼进 Prompt → 调用 LLM 生成回答
```

**Python（redis-py + RedisVL，最常用的组合）**

```python
from redisvl.index import SearchIndex
from redisvl.schema import IndexSchema
from redisvl.query import VectorQuery

schema = IndexSchema.from_dict({
    "index": {"name": "articles", "prefix": "article"},
    "fields": [
        {"name": "content", "type": "text"},

            "dims": 1536, "distance_metric": "cosine", "algorithm": "hnsw",
        }},
    ],
})
index = SearchIndex(schema, redis_url="redis://localhost:6379")
index.create(overwrite=True)

def embed(text: str) -> list[float]:
    # 调用你的 embedding 模型（OpenAI/本地模型/其他供应商），返回向量
    ...

def ingest(doc_id: str, content: str):
    index.load([{"id": doc_id, "content": content, "embedding": embed(content)}])

def retrieve(question: str, k: int = 5):
    query = VectorQuery(
        vector=embed(question), vector_field_name="embedding",
        num_results=k, return_fields=["content"],

```

## 15.4 语义缓存（Semantic Caching）：给 LLM 调用加一层"模糊命中"的缓存

这是这两年最实用的新模式，值得展开讲——它是原书第 2 章"页面缓存"思路的一次重大升级。

**原书第 2 章的缓存是精确匹配**：同一个请求（同一个 cache key）才能命中缓存。**LLM 调用的问题是**：用户问"Redis 怎么做限流"和"Redis 限流怎么实现"这两个提问文本不同，但语义几乎一致——精确匹配的缓存完全无法命中，导致重复调用昂贵的 LLM API。

**语义缓存的思路**：不按提问文本做精确匹配，而是把提问转成 embedding，如果历史提问里有语义足够接近（余弦相似度超过阈值，比如 0.95）的记录，直接返回之前缓存的回答，不再调用 LLM。

```python
import time
from redisvl.index import SearchIndex
from redisvl.query import VectorQuery

def semantic_cache_get(question: str, threshold: float = 0.95):
    vec = embed(question)
    query = VectorQuery(
        vector=vec, vector_field_name="embedding",
        num_results=1, return_fields=["question", "answer", "distance"],
    )
    results = cache_index.query(query)
    if results and (1 - results[0]["distance"]) >= threshold:
        return results[0]["answer"]
    return None

def answer_question(question: str) -> str:
    cached = semantic_cache_get(question)

    semantic_cache_set(question, answer)

```

**语义缓存的价值和风险都要说清楚**：

- **价值**：对于客服问答、FAQ 类高重复度场景，语义缓存能显著降低 LLM 调用成本和延迟（缓存命中是毫秒级的向量检索，LLM 调用通常是秒级）。
- **风险**：阈值设置不当会导致"错误命中"——两个语义相近但答案应该不同的问题（比如"如何删除用户 A 的数据"和"如何删除用户 B 的数据"）可能被误判为同一个缓存条目。**语义缓存不适合需要精确区分细节的场景**，更适合"重复率高、容错度也高"的通用问答。

## 15.5 何时该用 Redis 做向量存储，何时不该

**适合用 Redis**：

- 已经在用 Redis 做缓存/会话存储，想在同一套基础设施里加向量检索能力，不想引入新的中间件。
- 数据规模在千万级向量以内，且需要向量检索和传统过滤（标签、数值范围、全文）混合查询。
- 需要极低延迟（Redis 内存检索通常个位数毫秒级）。

**可能不适合/需要评估专用向量数据库**：

- 向量规模到十亿级以上，且主要工作负载就是纯向量检索——专用向量数据库（Milvus、Weaviate、Pinecone）在超大规模下的分片/压缩/量化能力通常更成熟。
- 需要复杂的向量索引调优（如多种量化策略、GPU 加速索引构建）。

这个判断逻辑和原书第 7 章结尾"到什么规模该放弃手写搜索、换专业搜索系统"的建议是同一个思路——**先用你已有的基础设施解决问题，规模/复杂度真正超出它的能力边界时，再引入专用系统**。

## 本章小结

Redis 通过 RediSearch 的向量字段，把"语义相似度检索"这个 2013 年完全不存在的需求，整合进了原书第 7 章讲的同一套"混合索引 + 排序"框架里——关键词过滤用的还是传统倒排索引，语义排序换成了向量距离，两者可以在一次查询里组合使用。语义缓存则是把原书第 2 章"精确匹配缓存"的思路，用向量相似度升级成"模糊匹配缓存"，是当前 LLM 应用里性价比很高的一个优化手段。理解这一章最好的方式，就是把它当成原书第 7 章在 AI 时代的自然延伸，而不是一个全新的话题。
