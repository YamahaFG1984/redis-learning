# 第 4 章 保障数据安全与性能

> 对应原书第 4 章 "Keeping data safe and ensuring performance"。这一章原书内容大多是"机制原理"，多数原理至今没变，但周边的工具和默认实践有明显进化，本文重点标注这些变化。

## 4.1 持久化：RDB 快照 + AOF

Redis 提供两种持久化机制，原书这部分的核心原理**至今完全适用**：

- **快照（RDB）**：某个时间点的全量数据落盘。触发方式：`BGSAVE`（fork 子进程写盘，不阻塞主进程）、`SAVE`（阻塞式，全内存都在做快照期间不能处理请求）、配置文件里的 `save <秒数> <变更次数>` 规则自动触发、`SHUTDOWN`/收到 TERM 信号时兜底保存一次、以及从库发起全量同步时。
- **AOF（Append-Only File）**：每条写命令都追加写入日志文件，可以完整重放恢复。`appendfsync` 三个选项：`always`（每次写都 fsync，最安全但吞吐受限于磁盘）、`everysec`（每秒 fsync 一次，官方推荐的折中方案）、`no`（交给操作系统决定，作者明确不推荐）。

**fork 开销的现实数据**（原书给出的经验值，今天依然是判断依据）：实体机/KVM 上 fork 大约 **10~20ms/GB**；作者当年在 Xen 虚拟化上（那时 AWS EC2 主流是 Xen）实测到 **200~300ms/GB**，50GB 数据 fork 耗时 15 秒以上、快照整体耗时 15~20 分钟，最后不得不改成"每晚 3 点暂停客户端写入 → SAVE → 备份 → 恢复写入"的笨办法。

**现代变化**：

- **AWS 等主流云厂商早已从 Xen 迁移到 KVM/Nitro 虚拟化**，fork 的虚拟化开销问题比 2013 年小得多，但"数据集越大、fork 停顿越长"这个基本规律没有变，**依然建议给 Redis 主节点预留 30~50% 的内存余量**用于 fork 和后台重写。
- **RDB+AOF 混合持久化**（Redis 4.0 起，`aof-use-rdb-preamble yes`，现在是默认值）：AOF 文件的开头是一份 RDB 格式的全量快照，后面才是增量命令日志——重启加载速度接近纯 RDB，同时保留了 AOF 的低数据丢失窗口。原书完全没有这个机制，因为它是 4.0 之后才引入的。
- **Multi Part AOF**（Redis 7.0 起）：AOF 目录被拆成 base 文件 + 一系列 incr 文件 + manifest 清单文件，`BGREWRITEAOF` 不再需要整体重写并替换一个巨大单文件，重写/清理更快、更安全。原书里"删除旧 AOF 文件本身可能造成系统卡顿几秒"这个问题，在多文件 AOF 机制下已经大幅缓解。
- SSD 上 `appendfsync always` 的写放大问题依然存在，但现代企业级 SSD 的寿命和吞吐相比 2013 年已经好了一个量级，这条建议的紧迫性有所下降，但**仍然不建议在普通云盘上无脑用 always**。

## 4.2 复制（Replication）

原书用 `SLAVEOF host port`（或配置文件里的 `slaveof`）配置主从复制，五步握手过程（连接→`SYNC`→全量快照传输→追平积压命令→切换实时流）在**协议层面已经被 Redis 2.8 引入的 `PSYNC`（部分重同步）大幅改进**：

- 原书的 `SYNC` 只支持全量同步——从库每次重连（哪怕只是短暂网络抖动）都要重新拉一份完整快照。
- **`PSYNC`**：主库维护一个复制积压缓冲区（replication backlog），从库短暂断线重连后，只要偏移量还在积压缓冲区范围内，就能做**增量**重同步，不需要重新全量传输。这是这些年复制机制最大的改进，直接解决了原书反复强调的"重连风暴导致带宽耗尽"问题的很大一部分。
- **无盘复制（diskless replication，`repl-diskless-sync yes`）**：主库可以直接把快照通过 socket 流式传给从库，不需要先落盘再传输，减少了大数据集下的额外磁盘 IO 和延迟。
- **`REPLICAOF`**：Redis 5.0 起，`SLAVEOF`/`SLAVEOF NO ONE` 的官方新名字是 `REPLICAOF`/`REPLICAOF NO ONE`（`master`/`slave` 术语逐步替换为 `primary`/`replica`），旧命令仍然作为别名保留兼容，但新代码/文档统一用新术语。
- **`WAIT` 命令**（2.8+）：`WAIT numreplicas timeout` 可以阻塞直到指定数量的副本确认收到了某个写操作——原书为了验证"写是否真的同步到从库/落盘"，手写了一个 `wait_for_sync()` 轮询函数（生成 UUID 令牌塞进 ZSET，反复轮询从库 `INFO`）；现代 Redis 有了官方命令，不再需要这种手工轮询。

**主主复制依然不支持**：原书明确警告过"Redis 不支持双主复制"，这一点到今天依然成立——Redis 的复制模型永远是树形的单向复制（一个主节点，若干从节点，从节点还可以有自己的从节点），没有 MySQL 那种双主/环形复制模式。如果需要多活写入，应该看 **Redis Enterprise 的 Active-Active（CRDT）** 或应用层自己做冲突消解。

### Redis Sentinel：从"即将完工"到成熟标配

原书写作时特意加了一个提示框："Redis Sentinel 是最近才加入的功能……到本书最终出版时应该已经完成"，并把 Sentinel 的详细使用推迟到第 10 章。**这句话放在今天读格外有意思**——Sentinel 早已是 Redis 高可用的标准组件：监控主从节点健康状态、多个 Sentinel 之间通过 gossip 达成共识、主库失联后自动选举新主、自动把其他从库指向新主、并支持故障切换通知钩子脚本。今天用 Redis 做高可用，Sentinel（或更进一步的 Redis Cluster 自带故障转移）几乎是必选项，不再是"实验性的新东西"。

## 4.3 处理系统故障

- **校验快照/AOF 完整性**：`redis-check-aof --fix` 可以截断到第一个损坏命令之前；RDB 快照**没有官方修复工具**（压缩格式导致中间损坏会连累后面全部不可读），作者建议保留多份备份、用 SHA1/SHA256 做校验（而不是 Redis 自带的 CRC64，因为 CRC 类校验和理论上可以被篡改者"配平"，SHA 系列没有已知的等效弱点）。这个建议在今天依然成立，且现代实践通常会进一步用**对象存储的版本控制/不可变备份**（如 S3 Object Lock）来防止备份被覆盖或删除。
- **手动故障转移流程**（原书 Listing 4.4）：SSH 到从库执行 `SAVE`，`scp` 快照到新主库，启动新主库，把原从库 `SLAVEOF` 指向新主库——这套手工流程在 Sentinel/Cluster 普及之后已经很少需要手动做，但理解它有助于理解 Sentinel 自动化了哪些步骤。

## 4.4 Redis 事务：WATCH/MULTI/EXEC

原书用"Fake Game Company"的游戏道具交易市场作为例子：

- `market:` ZSET，member 是 `"<itemid>.<sellerid>"`，score 是价格。
- `list_item()`：`WATCH` 卖家的 `inventory:<id>`，确认道具还在，`MULTI` 里做 `ZADD` 上架 + `SREM` 移出库存，`EXEC` 提交，`WatchError` 就重试。
- `purchase_item()`：同时 `WATCH` `market:` 和买家的 `users:<id>`，检查价格没变、余额够，`MULTI` 里转账 + 转移道具所有权。

**为什么 Redis 用乐观锁（WATCH）而不是悲观锁**：原书专门用一个侧栏解释——SQL 的 `SELECT FOR UPDATE` 会让客户端阻塞等待锁释放，Redis 选择让客户端在数据变化时收到通知/自动重试，永远不会阻塞等另一个客户端把事情做完。这个设计哲学至今没变。

**现代替代方案**：这套"WATCH + 重试"模式今天更常被 **Lua 脚本/Redis Functions** 替代——单个脚本天然原子，不需要处理 `WatchError` 重试逻辑（第 11 章会详细展开，也是原书自己在第 11 章重写这两个函数的理由）。

## 4.5 非事务性 Pipeline

原书区分了两种批量发送命令的方式：`conn.pipeline(True)`（包一层 MULTI/EXEC，事务性）和 `conn.pipeline(False)`（只是把多条命令打包一次发送，减少网络往返，但不保证原子性）——**MULTI/EXEC 本身也有开销，会阻塞其他客户端的命令**，所以如果不需要原子性，用非事务 pipeline 反而更快。

原书的实测数据表（`update_token()` 函数，pipeline vs 不 pipeline）：

| 网络环境 | 不 pipeline | pipeline |
|---|---|---|
| 本地 Unix socket | 3,761/s | 6,394/s |
| 本地 TCP | 3,257/s | 5,991/s |
| 同机房远程 | 739/s | 2,841/s |
| VPN 跨地域（48ms 延迟） | 3.67/s | 18.2/s |

结论：**延迟越高，pipeline 带来的收益越大**（跨地域场景提升近 5 倍），本地场景收益有限，因为瓶颈变成了单核 Python 编解码开销而不是网络。这个结论今天依然成立，且在今天的云环境里（跨可用区/跨区域延迟是常态）比 2013 年更值得重视。

## 4.6 性能诊断

原书给出一个至今非常实用的经验法则（Table 4.5）：

- Python 客户端单连接吞吐通常是 `redis-benchmark` 单客户端吞吐的 **50%~60%**——这是正常水平。
- 如果只达到 **25%~30%**，或者看到报错 **"Cannot assign requested address"**，几乎可以断定是**每次调用都重新建立连接，而不是复用连接池**。作者说这一条能解释"95% 的性能问题报告"。

这条诊断法则放到今天依然是排查 Redis 性能问题的第一步——**连接池配置错误**（尤其是在 Serverless/Lambda 这种每次调用可能冷启动新进程的环境里）仍然是最常见的 Redis 性能坑之一。现代客户端（redis-py、Jedis、ioredis/node-redis）都内置了连接池，但在 Serverless 场景下需要特别小心连接数爆炸的问题，通常建议搭配 **Redis 自带的连接数限制配置** 或者 **Amazon ElastiCache/MemoryDB 之类的托管代理层**。

## 现代实践补充：三语言的连接池与 Pipeline 示例

**Python（redis-py，连接池 + pipeline）**

```python
import redis

pool = redis.ConnectionPool(host="localhost", port=6379, max_connections=50)
r = redis.Redis(connection_pool=pool, decode_responses=True)

def update_token_pipeline(token: str, user: str, item: str | None = None):
    pipe = r.pipeline(transaction=False)  # 非事务 pipeline，只为减少往返
    pipe.hset("login:", token, user)
    pipe.zadd("recent:", {token: __import__("time").time()})
    if item:
        pipe.zadd(f"viewed:{token}", {item: 0})
        pipe.zremrangebyrank(f"viewed:{token}", 0, -26)
        pipe.zincrby("viewed:", -1, item)
    pipe.execute()
```

**Java（Jedis 连接池）**

```java
import redis.clients.jedis.JedisPool;
import redis.clients.jedis.JedisPoolConfig;
import redis.clients.jedis.Jedis;
import redis.clients.jedis.Pipeline;

JedisPoolConfig cfg = new JedisPoolConfig();
cfg.setMaxTotal(50);
JedisPool pool = new JedisPool(cfg, "localhost", 6379);

try (Jedis jedis = pool.getResource()) {
    Pipeline pipe = jedis.pipelined();
    pipe.hset("login:", token, user);
    pipe.zadd("recent:", System.currentTimeMillis() / 1000.0, token);
    pipe.sync(); // 一次性发送并等待所有结果
}
```

**TypeScript（ioredis 连接池由客户端内部管理，直接用 pipeline）**

```ts
import { Redis } from "ioredis";
const redis = new Redis({ maxRetriesPerRequest: 3 });

export async function updateTokenPipeline(token: string, user: string, item?: string) {
  const pipe = redis.pipeline(); // ioredis 的 pipeline 默认就是非事务批量；要事务用 redis.multi()
  pipe.hset("login:", token, user);
  pipe.zadd("recent:", Date.now() / 1000, token);
  if (item) {
    pipe.zadd(`viewed:${token}`, 0, item);
    pipe.zremrangebyrank(`viewed:${token}`, 0, -26);
    pipe.zincrby("viewed:", -1, item);
  }
  await pipe.exec();
}
```

## 4.7 本章小结

原书给出的两条核心结论至今没变：

1. 复制 + AOF 是保障数据安全的两大支柱。
2. `WATCH`/`MULTI`/`EXEC` 是防止并发客户端互相破坏数据的基础手段（现代实践中很大程度上被 Lua 脚本/Functions 取代，但原理相通）。

现代补充的第三条：**Sentinel/Redis Cluster 的自动故障转移，把原书第 4 章"手动 SSH 迁移主库"的应急预案，变成了日常配置的一部分**——理解手工流程仍有价值（尤其是排障时），但生产环境不应该再依赖纯手工故障转移。
