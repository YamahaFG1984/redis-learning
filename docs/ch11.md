# 第 11 章 用 Lua 给 Redis 写脚本

> 对应原书第 11 章 "Scripting Redis with Lua"，全书最后一个技术主题章节。Redis 2.6 首次引入 Lua 脚本能力，本章把前面几章的 WATCH/MULTI/EXEC、锁、信号量、自动补全、市场交易全部重写成 Lua 版本，用实测数据证明"用对了 Lua，代码更简单、性能更好"。

## 11.0 现代最重要的更新：Redis Functions

在深入本章内容之前，必须先说清楚这十年最大的变化：**Redis 7.0（2022 年）引入了 Redis Functions（`FUNCTION LOAD`/`FCALL`）**，它是 `EVAL`/`SCRIPT LOAD` 的官方"升级版"，直接解决了本章第一节要手工解决的问题：

- 原书 `script_load()` 自己实现了一个 SHA1 缓存 + `EVALSHA` 失败自动回退 `EVAL` 的包装器，因为 Redis 重启或 `SCRIPT FLUSH` 会让缓存的脚本哈希失效（`NOSCRIPT` 错误）。
- **Redis Functions 把脚本作为 RDB/AOF 持久化的一部分保存**，重启、`SCRIPT FLUSH` 都不会影响已注册的 Function，天然不需要"哈希缓存失效重试"这一整套逻辑。
- Functions 支持"库"的概念（一个库里可以定义多个函数），支持版本化，比裸 `EVAL` 脚本更适合作为**长期存在**的业务逻辑。

**什么时候还用 EVAL/EVALSHA**：一次性、临时、探索性的脚本依然适合直接 `EVAL`；需要长期稳定运行、多次调用的业务逻辑，现代实践优先用 Functions。本章讲的所有 Lua 脚本原理（KEYS/ARGV、原子性、可否中断）在 Functions 里完全适用，只是加载/持久化的机制更省心了。

## 11.1 不写 C 代码也能扩展 Redis

### 加载和调用脚本

`SCRIPT LOAD <script>` 把脚本编译缓存，返回 SHA1；`EVALSHA <sha> <numkeys> key... arg...` 用哈希调用，避免每次都传完整脚本体。

**KEYS 和 ARGV 的关键区别**：KEYS 参数是给未来的 Redis Cluster 用的——集群需要提前知道脚本会碰哪些 key，才能验证它们是否落在同一个哈希槽，拒绝跨槽脚本。ARGV 没有这个限制，只是纯数据。**这个设计意图在原书写作时是"面向未来"的（Cluster 2015 年才发布），今天已经是真实存在的约束**：如果你的 Lua 脚本/Function 要跑在 Redis Cluster 上，必须严格把所有涉及的 key 放进 KEYS，否则集群会拒绝执行或产生不可预期的结果。

**返回值类型转换表**（Lua → 客户端语言，原理没有变化）：`true`→1，`false`→nil/None，`nil`→截断后续返回值，浮点数→截断成整数，字符串/整数原样返回。原书建议尽量返回字符串手动解析，避免类型转换的歧义。

### 脚本的原子性与"不可中断"的风险

- **原子性**：`EVAL`/`EVALSHA`（以及 Functions 的 `FCALL`）在 Redis 眼里是**一条命令**，执行期间不会有其他命令插进来，比 MULTI/EXEC 隔离性更强。
- **风险**：Lua 是图灵完备的通用语言，一个死循环脚本会卡住整个 Redis。安全阀：如果脚本只做了读操作，超过 `lua-time-limit` 后可以用 `SCRIPT KILL` 杀掉；**如果脚本已经写了数据，`SCRIPT KILL` 不安全**（可能导致数据不一致），唯一的恢复手段是 `SHUTDOWN NOSAVE`（会丢失上次快照/AOF 之后的所有数据）。原书的忠告至今是铁律：**上线前必须充分测试 Lua 脚本**。

### 写 KEYS 之外的 key 会破坏 Cluster 兼容性

原书的 `create_status_lua` 脚本故意写了一个没有出现在 KEYS 参数里的 key（`status:<id>`，id 是脚本内生成的），用来演示"技术上可行，但破坏未来 Cluster 兼容性"——这一点今天不是"未来"而是"现实"：如果这个脚本要跑在 Redis Cluster 上，必须失败或产生错误路由。

## 11.2 用 Lua 重写锁和信号量

### 锁

原书用一个基准测试对比原始锁（SETNX+EXPIRE+WATCH 释放）和 Lua 版本（EXISTS+SETEX 获取，GET+DEL 原子释放）：**Lua 版本在 5/10 个并发客户端下，成功获取锁次数比原始版本多出 100%以上**，主要收益来自减少网络往返次数。

```lua
-- 获取锁
if redis.call('exists', KEYS[1]) == 0 then
    return redis.call('setex', KEYS[1], unpack(ARGV))
end
```

```lua
-- 释放锁
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1]) or true
end
```

### 信号量

Lua 版本把"清理过期持有者 + 检查名额 + 加入"打包成一次原子调用，**不再需要原书 6.3.2 节那套"计数器 ZSET + owner ZSET + 外层锁"的三层结构**——因为整个检查+写入过程本身就是原子的，天然公平，谁的脚本先执行谁就先拿到名额。这是本章最能体现"Lua 简化设计"的例子：原来需要三个数据结构配合一把锁才能保证正确，现在一个脚本就够了。

## 11.3 彻底告别 WATCH/MULTI/EXEC

### 自动补全重写

原书统计原始的公会自动补全函数（第 6 章的哨兵+WATCH 版本）大概 **40% 的代码量都在处理重试逻辑**。改写成 Lua 后不再需要任何重试代码。基准测试结果更有说服力：原始版本随并发数上升**成功次数反而下降**（10 个客户端时从 26,339 掉到 6,141，因为 WATCH 冲突重试太多），Lua 版本则持续上升到 128,217——**Lua 版本在 10 个并发客户端下处理的自动补全请求是原始版本的 20 倍以上**。

### 市场交易重写

原书把第 6 章"粗粒度锁 + WATCH 买家账户"的市场购买逻辑，简化成一个 Lua 脚本——查价格、查余额、扣款、转移物品、下架，全部在一次 `EVAL` 里完成，**不需要锁，也不需要 WATCH**。60 秒基准测试（5 卖家+5买家）对比：

| 方案 | 成交数 | 重试次数 | 平均延迟 |
|---|---|---|---|
| 不加锁 | &lt;600 | 161,000 | 498ms |
| 粗粒度锁 | 20,500 | 0 | 14ms |
| 细粒度锁 | 111,000 | 0 | &lt;3ms |
| **Lua** | **480,000** | **0** | **&lt;1ms**（实测约 0.61ms） |

Lua 版本比细粒度锁还快 **4.25 倍**。

**但作者明确指出 Lua 的边界**：脚本只能访问 Redis 内部能看到的数据，**不能在脚本执行过程中去调用外部数据库/API**——这是锁/WATCH 方案相对 Lua 的唯一优势场景。如果你的原子操作需要"读 Redis → 查外部系统 → 写回 Redis"，Lua 帮不上忙，还是得用锁。

## 11.4 用 Lua 给 LIST 分片

延续第 9 章"ZSET 不建议分片、LIST 分片很难不用 Lua"的伏笔，本节实现了一个支持双端阻塞/非阻塞推入弹出的分片 LIST：`<listname>:first`/`<listname>:last` 两个 key 记录当前首尾分片 ID，中间分片全部已满，只有首尾分片可能未满。

**明确的 Cluster 限制**：因为分片的具体 key 名字是脚本内部动态算出来的，没法提前通过 KEYS 声明，所以**这个分片 LIST 实现无法分布在 Redis Cluster 的多个节点上，只能跑在单个 Redis 实例内**——这是原书自己在侧栏承认的局限。

阻塞弹出的实现有一个很有意思的"骗术"：Redis 事务/脚本内部不能真正阻塞（会让整个服务器卡住等待），所以先在脚本里做非阻塞检查，如果确实为空，再单独发一个可能阻塞的 `BLPOP`/`BRPOP`，中间insert一个小 Lua 脚本检查分片 ID 是否变化，如果变了就推入一个"哨兵值"让阻塞调用立刻返回而不是傻等。作者坦诚承认这里依然有残余的竞态窗口，"每个系统都有它的局限"。

## 现代示例：Python/Java/TypeScript 调用 Lua 脚本

**Python（redis-py 原生 Script 支持，不需要自己写 SHA 缓存包装器）**

```python
import redis

r = redis.Redis(decode_responses=True)

PURCHASE_LUA = """
local price = tonumber(redis.call('zscore', KEYS[1], ARGV[1]))
local funds = tonumber(redis.call('hget', KEYS[2], 'funds'))
if price and funds and funds >= price then
    redis.call('hincrby', KEYS[3], 'funds', price)
    redis.call('hincrby', KEYS[2], 'funds', -price)
    redis.call('sadd', KEYS[4], ARGV[2])
    redis.call('zrem', KEYS[1], ARGV[1])
    return true
end
return false
"""

purchase_item = r.register_script(PURCHASE_LUA)  # redis-py 自动管理 SHA 缓存和 NOSCRIPT 回退

def purchase(buyer_id, item_id, seller_id, price):
    return purchase_item(
        keys=["market:", f"users:{buyer_id}", f"users:{seller_id}", f"inventory:{buyer_id}"],
        args=[f"{item_id}.{seller_id}", item_id],
    )
```

**Java（Jedis，直接 eval，或用 Redis Functions）**

```java
String luaScript = """
    local price = tonumber(redis.call('zscore', KEYS[1], ARGV[1]))
    local funds = tonumber(redis.call('hget', KEYS[2], 'funds'))
    if price and funds and funds >= price then
        redis.call('hincrby', KEYS[3], 'funds', price)

        redis.call('sadd', KEYS[4], ARGV[2])
        redis.call('zrem', KEYS[1], ARGV[1])

    end

    """;

Object result = jedis.eval(
    luaScript,
    List.of("market:", "users:" + buyerId, "users:" + sellerId, "inventory:" + buyerId),

```

**TypeScript（ioredis，用 `defineCommand` 注册可复用命令）**

```ts
import { Redis } from "ioredis";

const redis = new Redis();

redis.defineCommand("purchaseItem", {
  numberOfKeys: 4,
  lua: `
    local price = tonumber(redis.call('zscore', KEYS[1], ARGV[1]))
    local funds = tonumber(redis.call('hget', KEYS[2], 'funds'))
    if price and funds and funds >= price then
        redis.call('hincrby', KEYS[3], 'funds', price)
        redis.call('hincrby', KEYS[2], 'funds', -price)
        redis.call('sadd', KEYS[4], ARGV[2])
        redis.call('zrem', KEYS[1], ARGV[1])
        return 1
    end
    return 0
  `,
});

// @ts-expect-error ioredis 动态注入的方法
const result = await redis.purchaseItem(
  "market:", `users:${buyerId}`, `users:${sellerId}`, `inventory:${buyerId}`,
  `${itemId}.${sellerId}`, itemId,
);
```

## 现代示例：用 Redis Functions 替代手写 SHA 缓存包装器

Redis 7+ 推荐用 Functions 承载"长期存在"的业务逻辑，注册一次，重启/FLUSH 都不受影响：

```lua
#!lua name=marketplace

redis.register_function('purchase_item', function(keys, args)
    local price = tonumber(redis.call('zscore', keys[1], args[1]))
    local funds = tonumber(redis.call('hget', keys[2], 'funds'))
    if price and funds and funds >= price then
        redis.call('hincrby', keys[3], 'funds', price)
        redis.call('hincrby', keys[2], 'funds', -price)
        redis.call('sadd', keys[4], args[2])
        redis.call('zrem', keys[1], args[1])
        return 1
    end
    return 0
end)
```

```bash
redis-cli -x FUNCTION LOAD < marketplace.lua
redis-cli FCALL purchase_item 4 market: users:27 users:17 inventory:27 "M.17" "M"
```

## 本章小结

原书的核心结论——"Lua 脚本能大幅简化代码、大幅提升并发性能，代价是脚本内部访问不到外部系统"——放到今天完全成立，而且有了更好的官方支撑：**Redis Functions 解决了原书第一节手工解决的"脚本缓存失效"问题，让 Lua 方案更适合作为长期业务逻辑存在**。本章展示的三个基准测试（锁、自动补全、市场交易）用真实数字证明了一个反复出现的主题：**能用一次原子脚本解决的问题，通常比"客户端多次往返+重试"更快、更简单**——这是贯穿全书从第 1 章的竞态问题到第 11 章的最终解法的一条主线。
