# 第 13 章（补充）用 Redis 做限流

> 本章是原书没有覆盖的内容。原书第 6 章的计数信号量解决的是"并发数限制"（同一时刻最多 N 个持有者），而**限流（rate limiting）解决的是"单位时间内最多 N 次请求"**——这是今天几乎所有 API 网关、SaaS 计费、防刷系统里最高频的 Redis 用例之一，原书完全没有专门讨论。

## 13.0 为什么限流现在这么重要

2013 年互联网的 API 生态远没有今天这么开放——今天几乎每个对外接口都要考虑：单个用户/IP/API Key 的调用频率上限、防止爬虫/刷单、按套餐分级限流（免费版 100 次/分钟，付费版 10000 次/分钟）、保护后端脆弱依赖（比如调用第三方短信/支付接口有配额）。Redis 天然适合做限流的原因和原书全书的主题一致：**限流需要极低延迟的原子计数，Redis 内存操作 + 原子命令正好满足这个需求**。

## 13.1 固定窗口计数器（最简单，但有边界问题）

最直观的实现：每个时间窗口一个 key，`INCR` 计数，第一次访问时设置过期时间。

```lua
-- fixed_window.lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])

local current = redis.call('INCR', key)
if current == 1 then
    redis.call('EXPIRE', key, window)
end
if current > limit then
    return 0  -- 拒绝
end
return 1      -- 允许
```

**已知问题**：固定窗口在边界处会出现"双倍突发"——比如限制是"每分钟 100 次"，用户可以在第 59 秒发 100 次，第 61 秒（新窗口开始）再发 100 次，2 秒内实际通过了 200 次请求，远超预期的限流强度。这是固定窗口算法广为人知的缺陷，几乎所有讲限流的资料都会提到。

## 13.2 滑动窗口日志（精确，但耗内存）

用 ZSET 存每次请求的时间戳作为 score，每次请求先清理窗口外的旧记录，再看窗口内还剩多少配额：

```lua
-- sliding_window_log.lua
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, now .. '-' .. math.random())
    redis.call('EXPIRE', key, window)
    return 1
end
return 0
```

**精确但代价高**：每个请求都要存一条 ZSET 成员，高频场景下内存占用和命令开销都比固定窗口大很多——这正是原书第 6 章计数信号量用到的同一个 ZSET 模式（清理过期成员 + 检查数量），只是应用场景从"并发限制"换成了"频率限制"。

## 13.3 滑动窗口计数器（工程上最常用的折中方案）

结合固定窗口的低开销和滑动窗口的精确性：用当前窗口和上一个窗口的计数按比例加权估算。这是 Cloudflare 等公司公开分享过的生产方案：

```lua
-- sliding_window_counter.lua
local key_prefix = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])   -- 窗口大小，如 60 秒
local limit = tonumber(ARGV[3])

local current_window = math.floor(now / window)
local previous_window = current_window - 1
local elapsed_ratio = (now % window) / window

local current_key = key_prefix .. ':' .. current_window
local previous_key = key_prefix .. ':' .. previous_window

local current_count = tonumber(redis.call('GET', current_key) or '0')
local previous_count = tonumber(redis.call('GET', previous_key) or '0')

-- 加权估算：越接近当前窗口末尾，上一个窗口的权重越低
local estimated = previous_count * (1 - elapsed_ratio) + current_count

if estimated >= limit then
    return 0
end

redis.call('INCR', current_key)
redis.call('EXPIRE', current_key, window * 2)
return 1
```

## 13.4 令牌桶（Token Bucket）—— 允许突发流量的场景

令牌桶允许短时间内的突发请求（只要桶里有攒下的令牌），比滑动窗口更贴近真实用户行为（用户不是均匀发请求的）。

```lua
-- token_bucket.lua
local key = KEYS[1]
local now = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])       -- 每秒生成的令牌数
local capacity = tonumber(ARGV[3])   -- 桶容量
local requested = tonumber(ARGV[4])  -- 本次请求消耗的令牌数

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1])
local last_refill = tonumber(bucket[2])

if tokens == nil then
    tokens = capacity
    last_refill = now
end

local delta = math.max(0, now - last_refill)
tokens = math.min(capacity, tokens + delta * rate)

if tokens >= requested then
    tokens = tokens - requested
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)
    return 1
end

redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)
return 0
```

## 13.5 官方/现成方案：redis-cell 模块与 GCRA 算法

如果不想自己维护 Lua 脚本，Redis 有一个现成的限流模块 **redis-cell**（实现 GCRA——Generic Cell Rate Algorithm，本质是令牌桶的一种数学等价形式），提供 `CL.THROTTLE` 命令：

```
CL.THROTTLE user123 15 30 60
--          key      最大突发 每60秒30次 时间窗口
```

一条命令返回是否允许、剩余配额、下次重试等待时间——不需要自己写 Lua 脚本、不需要处理边界情况。生产环境如果 Redis 部署方式支持加载模块（如自建、Redis Stack），**优先用 `redis-cell` 而不是重新发明轮子**；如果是不支持自定义模块的托管服务（部分云厂商的基础版托管 Redis 不支持模块），退回到上面 13.3/13.4 节的 Lua 脚本方案。

## 13.6 三语言实现：滑动窗口计数器限流器

**Python（redis-py，register_script）**

```python
import time
import redis

r = redis.Redis(decode_responses=True)

SLIDING_WINDOW_LUA = """
local current_window = math.floor(tonumber(ARGV[1]) / tonumber(ARGV[2]))
local previous_window = current_window - 1
local elapsed_ratio = (tonumber(ARGV[1]) % tonumber(ARGV[2])) / tonumber(ARGV[2])
local current_key = KEYS[1] .. ':' .. current_window
local previous_key = KEYS[1] .. ':' .. previous_window
local current_count = tonumber(redis.call('GET', current_key) or '0')
local previous_count = tonumber(redis.call('GET', previous_key) or '0')
local estimated = previous_count * (1 - elapsed_ratio) + current_count
if estimated >= tonumber(ARGV[3]) then
    return 0
end
redis.call('INCR', current_key)
redis.call('EXPIRE', current_key, tonumber(ARGV[2]) * 2)
return 1
"""
rate_limit = r.register_script(SLIDING_WINDOW_LUA)

def is_allowed(identifier: str, limit: int = 100, window: int = 60) -> bool:
    result = rate_limit(keys=[f"ratelimit:{identifier}"], args=[time.time(), window, limit])
    return bool(result)
```

**Java（Jedis）**

```java
public boolean isAllowed(UnifiedJedis jedis, String identifier, int limit, int windowSeconds) {
    String lua = """
        local current_window = math.floor(tonumber(ARGV[1]) / tonumber(ARGV[2]))
        local previous_window = current_window - 1
        local elapsed_ratio = (tonumber(ARGV[1]) % tonumber(ARGV[2])) / tonumber(ARGV[2])
        local current_key = KEYS[1] .. ':' .. current_window
        local previous_key = KEYS[1] .. ':' .. previous_window
        local current_count = tonumber(redis.call('GET', current_key) or '0')
        local previous_count = tonumber(redis.call('GET', previous_key) or '0')
        local estimated = previous_count * (1 - elapsed_ratio) + current_count
        if estimated >= tonumber(ARGV[3]) then return 0 end
        redis.call('INCR', current_key)
        redis.call('EXPIRE', current_key, tonumber(ARGV[2]) * 2)
        return 1
        """;
    Object result = jedis.eval(
        lua,
        List.of("ratelimit:" + identifier),
        List.of(String.valueOf(System.currentTimeMillis() / 1000.0), String.valueOf(windowSeconds), String.valueOf(limit))
    );
    return Long.valueOf(1).equals(result);
}
```

**TypeScript（ioredis + Hono.js 中间件，最贴近实际业务场景）**

```ts
import { Redis } from "ioredis";

const redis = new Redis();

const SLIDING_WINDOW_LUA = `
local current_window = math.floor(tonumber(ARGV[1]) / tonumber(ARGV[2]))
local previous_window = current_window - 1
local elapsed_ratio = (tonumber(ARGV[1]) % tonumber(ARGV[2])) / tonumber(ARGV[2])
local current_key = KEYS[1] .. ':' .. current_window
local previous_key = KEYS[1] .. ':' .. previous_window
local current_count = tonumber(redis.call('GET', current_key) or '0')
local previous_count = tonumber(redis.call('GET', previous_key) or '0')
local estimated = previous_count * (1 - elapsed_ratio) + current_count
if estimated >= tonumber(ARGV[3]) then return 0 end
redis.call('INCR', current_key)
redis.call('EXPIRE', current_key, tonumber(ARGV[2]) * 2)
return 1
`;

redis.defineCommand("slidingWindowLimit", { numberOfKeys: 1, lua: SLIDING_WINDOW_LUA });

export async function isAllowed(identifier: string, limit = 100, window = 60): Promise<boolean> {
  // @ts-expect-error ioredis 动态注入
  const result = await redis.slidingWindowLimit(`ratelimit:${identifier}`, Date.now() / 1000, window, limit);
  return result === 1;
}
```

```ts
// Hono.js 限流中间件
import { Hono } from "hono";
import type { MiddlewareHandler } from "hono";

function rateLimiter(limit = 100, window = 60): MiddlewareHandler {
  return async (c, next) => {
    const identifier = c.req.header("x-api-key") ?? c.req.header("cf-connecting-ip") ?? "anonymous";
    const allowed = await isAllowed(identifier, limit, window);
    if (!allowed) {
      return c.json({ error: "Too Many Requests" }, 429);
    }
    await next();
  };
}

const app = new Hono();
app.use("/api/*", rateLimiter(100, 60));
app.get("/api/hello", (c) => c.json({ message: "ok" }));

export default app;
```

## 13.7 分布式场景下的注意事项

- **多个 API 网关实例共享同一个 Redis** 才能实现全局限流；如果每个网关实例自己在内存里计数，只能做到"单机限流"，全局限额会被实例数放大。
- **限流 key 的设计要考虑 Redis Cluster**：如果限流 key 是 `ratelimit:<user_id>:<window>`，在 Cluster 下会天然按 `user_id` 哈希分散到不同分片，这通常是期望的行为（不同用户的限流互不影响，天然可以水平扩展）。
- **限流不应该成为新的单点故障**：如果 Redis 短暂不可用，限流中间件要有明确的降级策略——是"直接放行"（fail-open，优先保证可用性）还是"直接拒绝"（fail-closed，优先保证限流语义不被绕过），需要根据业务场景权衡，一般对外 API 网关更倾向 fail-open。

## 本章小结

原书没有专门讲限流，但第 6 章的计数信号量、第 2 章的清理循环，在设计思路上和限流算法一脉相承——都是"用 Redis 的原子操作在极短时间内做出允许/拒绝的判断"。今天的限流实践比原书年代成熟得多：固定窗口简单但有边界突发问题，滑动窗口日志精确但耗内存，滑动窗口计数器是工程上最常见的折中方案，令牌桶适合允许突发流量的场景，而 `redis-cell` 模块的 GCRA 算法则是"不想自己维护 Lua 脚本"时的现成答案。
