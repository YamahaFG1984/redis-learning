# 第 12 章（补充）安全与访问控制

> 本章是原书没有覆盖的内容。《Redis in Action》写于 2013 年，当时 Redis 的安全模型极其简陋——一个全局密码（`requirepass`），要么全权限访问，要么什么都不能做。这些年 Redis 的安全能力有了质的飞跃，本章按现代实践重新梳理。

## 12.0 为什么原书完全没讲安全

2013 年的 Redis 默认假设：**Redis 永远部署在受信任的内网里，前面挡着应用服务器，永远不直接暴露给外部流量**。这个假设在当时基本成立，但这些年因为大量 Redis 实例被误配置直接暴露在公网（默认无密码、默认监听 0.0.0.0），造成了大规模的数据泄露和勒索事件（攻击者扫描到无密码 Redis 后写入恶意 key、甚至通过 `CONFIG SET dir`+`SAVE` 往服务器写 SSH 公钥/webshell）。**这段历史直接推动了 Redis 安全模型的现代化**——理解这段"血泪史"，比单纯背命令更重要。

## 12.1 网络层：默认最小暴露面

**永远不要相信"内网就是安全的"**：

- `bind 127.0.0.1 -::1`：默认只监听本地回环地址；如果要跨机器访问，显式绑定到内网网卡地址，**永远不要绑定 `0.0.0.0` 除非有防火墙/安全组严格限制**。
- `protected-mode yes`（Redis 3.2+ 默认开启）：如果没设密码又监听了非回环地址，Redis 会拒绝外部连接并在日志里警告——这是专门为了防止"忘记设密码就暴露公网"这种最常见的事故加的保险丝。
- 云环境优先用安全组/VPC 网络隔离，而不是仅依赖 Redis 自身的认证——认证是最后一道防线，不是唯一防线。
- 生产环境启用 **TLS**（Redis 6.0+ 原生支持，不再需要 stunnel 之类的额外代理）：

```bash
redis-server --tls-port 6379 --port 0 \
  --tls-cert-file /path/redis.crt \
  --tls-key-file /path/redis.key \
  --tls-ca-cert-file /path/ca.crt
```

## 12.2 认证：从 `requirepass` 到 ACL

### 老办法（原书时代唯一的选择）

```
requirepass your-strong-password
```

所有客户端共用一个密码，要么全权限，要么拒绝——**没有"只读账号""只允许访问某几个 key""禁止执行 FLUSHALL"这类精细化控制**。这是原书年代 Redis 安全模型的根本局限。

### 现代方案：ACL（Redis 6.0+）

ACL 允许你定义多个用户，每个用户可以限定：能执行哪些命令、能访问哪些 key 模式、密码是什么。

```bash
# 只读用户，只能访问 cache: 前缀的 key
ACL SETUSER readonly_app on >strong-password ~cache:* +get +mget +exists -@all +@read

# 一个只能执行特定业务命令的应用账号（最小权限原则）
ACL SETUSER order_service on >another-password \
    ~order:* ~inventory:* \
    +get +set +hset +hget +hgetall +expire +eval

# 查看当前有哪些用户和权限
ACL LIST
ACL WHOAMI
ACL CAT           # 查看所有命令分类（@read/@write/@dangerous/@admin...）
```

**关键实践**：

- **永远不要用默认的 `default` 用户跑生产业务**——建议禁用或至少给它设强密码，为每个应用/微服务单独建 ACL 用户，遵循最小权限原则。
- 用 `-@dangerous` 屏蔽掉 `FLUSHALL`/`FLUSHDB`/`CONFIG`/`SHUTDOWN`/`DEBUG` 这类高危命令，应用账号通常不需要执行它们。
- ACL 规则可以写进 `users.acl` 外部文件（`aclfile /path/users.acl`），配合 `ACL LOAD`/`ACL SAVE` 做持久化管理，而不是每次重启都用命令行重新声明。
- 生产环境建议给每个客户端应用/团队分配独立账号，这样**审计日志能追溯到具体是谁的连接做了什么**（配合 `ACL LOG` 查看权限拒绝事件）。

## 12.3 三语言下的安全连接示例

**Python（redis-py，TLS + ACL 用户）**

```python
import redis

r = redis.Redis(
    host="redis.internal.example.com",
    port=6379,
    username="order_service",       # ACL 用户名，不再是只有密码
    password="another-password",
    ssl=True,
    ssl_ca_certs="/path/ca.crt",
    decode_responses=True,
)
r.ping()
```

**Java（Jedis，TLS + ACL）**

```java
import redis.clients.jedis.UnifiedJedis;
import redis.clients.jedis.JedisURI;

UnifiedJedis jedis = new UnifiedJedis(
    "rediss://order_service:another-password@redis.internal.example.com:6379"
); // rediss:// 前缀启用 TLS
```

**TypeScript（ioredis，TLS + ACL）**

```ts
import { Redis } from "ioredis";

const redis = new Redis({
  host: "redis.internal.example.com",
  port: 6379,
  username: "order_service",
  password: "another-password",
  tls: { ca: [require("fs").readFileSync("/path/ca.crt")] },
});
```

## 12.4 数据层面的安全考量

- **敏感数据不要明文存进 Redis**：Redis 的持久化文件（RDB/AOF）、`MONITOR` 命令输出、慢查询日志都可能明文暴露 key/value——如果必须缓存 PII（个人身份信息）或密钥类数据，应用层加密后再存，或者压根不缓存。
- **`KEYS *`/`MONITOR`/`FLUSHALL` 这类命令建议用 ACL 禁掉**，或者改名（`rename-command`，虽然 Redis 7 之后官方更推荐用 ACL 而不是改名，改名容易在集群/多实例环境下管理混乱）。
- **命令注入类风险**：如果业务代码把用户输入直接拼进 Lua 脚本或命令参数（而不是作为 `ARGV`/参数传入），可能造成类似 SQL 注入的问题——**永远用参数化调用，不要用字符串拼接构造 Redis 命令或 Lua 脚本**。
- 反序列化风险：如果 value 里存的是 pickle（Python）或 Java 序列化对象，从 Redis 读出来再反序列化，等同于信任了写入方——如果写入方可能被攻破（比如另一个不完全受信的微服务共用同一个 Redis），要小心反序列化漏洞，优先用 JSON 这类无代码执行能力的格式。

## 12.5 生产安全清单（Checklist）

- [ ] 只监听内网地址；`protected-mode yes`。
- [ ] 启用 TLS（尤其是跨可用区/跨云传输）。
- [ ] 用 ACL 给每个应用建独立最小权限账号，不用 `default` 用户跑业务。
- [ ] 高危命令（`FLUSHALL`/`CONFIG`/`SHUTDOWN`/`DEBUG`/`KEYS`）通过 ACL 限制给运维账号专用。
- [ ] 密码/密钥走 Secrets Manager（AWS Secrets Manager、HashiCorp Vault），不要写死在配置文件或代码里。
- [ ] 敏感数据加密后再进 Redis，或干脆不缓存。
- [ ] 定期检查 `ACL LOG` 和慢查询日志，留意异常访问模式。
- [ ] 云托管场景确认安全组/VPC 规则，Redis 端口不应对公网开放。

## 本章小结

原书完全没有安全章节，是因为 2013 年的 Redis 生态默认"你的内网是安全的"。今天的现实是：Redis 实例暴露在公网、被脚本扫描并利用是**每天都在发生**的真实攻击面。现代 Redis 用 ACL 补齐了"最小权限"这个关键能力，TLS 补齐了传输加密，`protected-mode` 补齐了"忘记设密码"这个最常见事故的兜底——这三件事应该是任何 2020 年之后新上线的 Redis 实例的标配检查项，而不是可选项。
