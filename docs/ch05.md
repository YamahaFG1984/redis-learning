# 第 5 章 用 Redis 支撑应用运维

> 对应原书第 5 章 "Using Redis for application support"。这一章讲的是"用 Redis 给系统本身提供支撑"——日志、计数器/统计、IP 归属地查询、服务发现与配置管理，而不是直接面向业务功能。

## 5.1 日志

原书对比传统方案：各程序自己写文件（没有统一的轮转/清理）vs syslog（统一收集，但依然是"扔到磁盘文件里"）。提出用 Redis 做**短期、时效性强**的日志视图，磁盘/syslog 仍然作为长期存档。

### 最近日志

`LPUSH` 写入一个 LIST，`LTRIM` 裁剪到固定条数（书中设为 100），`LRANGE` 读取——非常直接的滑动窗口模式。

### 高频日志（按出现次数排序）

用 ZSET，`ZINCRBY` 累加每条消息的出现次数，每小时轮转一次（把当前 ZSET `RENAME` 成 `:last` 归档，开一个新的），用 `WATCH`/`MULTI`/`EXEC` 检测跨小时边界的竞态。

**现代视角**：这一整套"往 Redis 里写日志"的模式，在 2013 年之后已经被更专业的日志基础设施大量取代——**ELK/EFK 栈（Elasticsearch+Logstash/Fluentd+Kibana）、Loki+Grafana、云厂商的日志服务（CloudWatch Logs、阿里云 SLS）** 都是更成熟的选择。如果你今天要做"最近日志滚动窗口"这种轻量需求，Redis LIST/ZSET 依然是一个便宜好用的方案，但**如果需要全文检索、长期存储、多维度聚合，直接上专业日志系统而不是在 Redis 里手搭**。

## 5.2 计数器与统计

### 多精度时间序列计数器

原书设计：一个名字在 7 种精度（1秒/5秒/1分钟/5分钟/1小时/5小时/1天）下各维护一个 HASH，字段是时间片起始时间戳，值是计数；再用一个 `known:` ZSET（所有分数设成 0，退化成按名字字典序排列）记录"当前有哪些计数器存在"，供清理进程遍历。

**为什么不能直接用 EXPIRE**：原书专门开了一个侧栏解释——一个 HASH key 里存的是**同一个计数器所有时间片**的数据，`EXPIRE` 只能整体删除这个 key，没法单独让某个字段（某个时间片）过期。

**现代视角这一点已经被部分解决**：前面第 3 章提到的 **Redis 7.4 `HEXPIRE`** 系列命令，可以直接给 HASH 的单个字段设置 TTL——如果今天重新设计这个计数器方案，完全可以把"时间片→计数"的每个字段单独设置过期时间，不再需要原书这套"轮询扫描 `known:` ZSET、按精度决定清理频率、WATCH/MULTI/EXEC 保护空 HASH 删除"的复杂清理逻辑。

**更进一步的现代方案**：真正需要严肃时间序列指标的场景，建议直接上 **RedisTimeSeries 模块**（现已合入 Redis Stack/Redis 8）——原生支持多精度降采样（downsampling）、保留策略（retention policy）、聚合规则，比原书手写的多精度 HASH 方案能力强得多，也不需要自己写清理循环。

### 统计（均值/标准差）

用一个 ZSET 存 `min`/`max`/`count`/`sum`/`sumsq` 五个"成员"，靠 `ZUNIONSTORE`（aggregate=min/max）避免用 `WATCH` 争抢一个高频更新的统计 key。作者提到自己"亲测了 5 种不同的统计存储方案"才收敛到这个设计——这是一个很好的提醒：**看起来简单的统计需求，在高并发写入下也需要仔细的数据结构设计**。

**现代替代**：`update_stats()`这类自定义统计逻辑，在今天更常见的做法是直接接入 **Prometheus（client 库在应用内埋点，pull 模型）+ Grafana**，或者用 RedisTimeSeries 的聚合规则代替手写 ZUNIONSTORE 技巧。原书自己也在侧栏推荐 Graphite（当年最流行的开源监控方案）而不是从零造轮子，这个建议至今没变——**指标采集/可视化不要自己造，除非你有非常特殊的需求**。

## 5.3 IP 归属地查询

原书用 MaxMind 的免费 **GeoLite City** 数据库（两个 CSV：IP 段→城市 ID，城市 ID→城市/地区/国家名），把 IP 转成 32 位整数，存进一个 ZSET（分数是 IP 整数值），查询时用 `ZREVRANGEBYSCORE` 找到"小于等于目标 IP 的最大范围起点"。

**现代变化（重要）**：

- **MaxMind 的免费产品已经从 GeoLite City（CSV 格式）演进为 GeoLite2（MMDB 二进制格式）**，原书用的 CSV 下载链接和字段格式已经过时；现在推荐直接用 MaxMind 官方的 `geoip2` 客户端库读取 `.mmdb` 文件，或者用 `maxminddb` 这类库做本地查询，不再需要手工把整个数据集导入 Redis。
- 如果确实需要把 IP 段数据放进 Redis 供多服务共享查询，原书这个"IP 转整数 + ZSET range 查找"的技巧本身依然成立，且第 7 章会说这是一个通用的"把非数值数据转换成可排序分数"模式（后面章节的字符串转分数技巧是同一个思路）。
- **一个更现代的选择**：直接用云服务商的 IP 地理位置 API（如 Cloudflare 在边缘节点自带的 `CF-IPCountry` 头、AWS CloudFront 的地理位置头），如果你的流量本来就经过 CDN/边缘网络，很多时候不需要自己维护这份数据。

## 5.4 服务发现与配置

原书的核心思路：与其把配置写在配置文件里挨个分发/重启服务，不如把配置存在 Redis 里，所有服务读同一份"真相"。

- `is_under_maintenance()`：用模块级全局变量做 1 秒缓存，避免高并发下每个请求都打一次 Redis（作者特意提到"用户疯狂刷新维护页面"这种场景）。
- `set_config()`/`get_config()`：JSON 编码配置存进 `config:<type>:<component>` 这个 key，同样带一个可调节的缓存窗口（`wait` 参数）。
- `redis_connection()` 装饰器：自动读取配置、按需创建/复用连接，调用方不再需要手动传连接对象——这是 Python 装饰器模式在基础设施代码里的一个典型应用。

**现代视角**：这套"拿 Redis 当配置中心/服务发现"的方案，在今天的生态里通常会被更专业的工具替代：

- **服务发现/配置中心**：Consul、etcd、ZooKeeper、云厂商的 Parameter Store/Secrets Manager，都比"手写 JSON 存 Redis + 客户端轮询"更成熟（支持 watch 机制、强一致性、权限管理）。
- 但如果你的场景足够简单（比如只是"给所有实例广播一个全局开关"），Redis 依然是最低成本的方案——**这个装饰器思路在小型系统里今天仍然实用**，尤其是搭配 Redis 的 **keyspace notification**（订阅 key 变更事件）可以做到比"轮询 + 1 秒缓存"更实时的配置推送，而不需要自己实现轮询。

### 现代示例：用 Keyspace Notification 替代轮询式配置刷新

**Python（redis-py）**

```python
import json
import redis

r = redis.Redis(decode_responses=True)
r.config_set("notify-keyspace-events", "KEA")  # 开启 keyspace 通知

_config_cache: dict[str, dict] = {}

def get_config(component: str) -> dict:
    if component not in _config_cache:
        raw = r.get(f"config:{component}")
        _config_cache[component] = json.loads(raw) if raw else {}
    return _config_cache[component]

def watch_config_changes():
    pubsub = r.pubsub()
    pubsub.psubscribe("__keyspace@0__:config:*")
    for msg in pubsub.listen():
        if msg["type"] != "pmessage":
            continue
        key = msg["channel"].split(":", 1)[1]
        component = key.split(":", 1)[1]
        raw = r.get(key)
        _config_cache[component] = json.loads(raw) if raw else {}
```

**TypeScript（ioredis + Hono.js，暴露一个健康检查/配置端点）**

```ts
import { Hono } from "hono";
import { Redis } from "ioredis";

const redis = new Redis();
const sub = new Redis();
const configCache = new Map<string, unknown>();

sub.psubscribe("__keyspace@0__:config:*");
sub.on("pmessage", async (_pattern, channel) => {
  const key = channel.split(":").slice(1).join(":");
  const component = key.split(":")[1];
  const raw = await redis.get(key);
  configCache.set(component, raw ? JSON.parse(raw) : null);
});

const app = new Hono();
app.get("/config/:component", (c) => {
  const component = c.req.param("component");
  return c.json(configCache.get(component) ?? {});
});

export default app;
```

## 本章小结

原书这一章的三个方向（日志/统计、IP 归属地、服务发现配置）在今天都有了更专业的替代品：Prometheus/Grafana/RedisTimeSeries 替代手写统计，MaxMind GeoLite2 + 边缘网络头替代手工 IP 表，Consul/etcd 替代 Redis 配置中心。但原书教的**设计思路**——用 ZSET 做多精度滚动窗口、用装饰器自动管理连接、用短 TTL 本地缓存减少 Redis 压力——依然是构建轻量级基础设施代码时非常实用的模式，尤其适合不想引入额外中间件的小型项目。
